> **用途**：① 定位自己的真实水平 ② 面试前自检 ③ 后续补缺的依据

## 二、正向对照：哪些已经高于入门线

**这一节是给面试用的 —— 但也必须诚实，所以每条都写"为什么它稀缺"。**

| # | 能力 | 为什么稀缺 |
| --- | --- | --- |
| 1 | **同一件事写两遍**（手写 ReAct + LangGraph），并对比出差异 | 大多数人只用过一个框架，说不出"框架给什么、不给什么" |
| 2 | **量化"工具输出"对能力的影响**（5/5 → 0/1 反问） | 大多数人以为工具就是"接口"，不知道**它给什么，模型才能用什么** |
| 3 | **失败模式有实测记录**（工具异常 / 预算耗尽 / 字段塌缩 / 截断） | 大多数人只会说"我加了重试和兜底" |
| 4 | **架构判断有数据**（RAG vs Agent 的四行对比） | 大多数人只会说"我用了 Agent" |
| 5 | **协议层踩过真坑**（MCP v2 改名、docstring 不解析、camelCase vs snake_case） | 大多数人只看过教程，没跑过端到端 |
| 6 | **能把"机制"和"模型行为"分开测** | 这是工程素养：用无 LLM 的最小图验证框架语义 |
| 7 | **每一条结论都有"反过来会怎样"** | 35 条决策记录都写了反面，这是架构判断力的证据 |

**一句话**：你的优势不在"会用什么框架"，而在 **"能证明自己哪里错了"**。

## 三、反向对照：工业级的六个硬指标

| # | 工业级要求 | 现状 | 差距 |
| --- | --- | --- | --- |
| 1 | **有 eval 集，改 prompt 能量化效果** | ❌ 完全没有 | **最大** |
| 2 | **有 trace，能回答"为什么这次跑了 7 步"** | 🟡 只有分段耗时 | 中 |
| 3 | **降级路径确定**（模型挂 / 工具挂 / 超预算） | 🟡 部分有，未系统验证 | 中 |
| 4 | **权限与安全**（工具级鉴权、提示注入、审计） | ❌ 完全没有 | **大** |
| 5 | **成本控制**（token / 步数预算、模型分级） | ❌ 没有 | 中 |
| 6 | 流式 + 进度反馈（用户不等 30 秒） | 🟡 LLM 层有 stream，Agent 层没有 | 小 |

### 逐条说清

**① eval —— 分水岭**

工业界判断一个人会不会做 Agent，**第一个问题就是"你怎么知道改完更好了"**。

现在能回答的是"我跑了 3 次"—— **那不是 eval**。

最小可用的 eval：

```
20 个问题 × (期望关键词 + 期望引用的 chunk_id + 禁止出现的表述)
→ 准确率 / 引用命中率 / 编造率 / 平均步数 / 失败类型分布
```

**成本和价值**：半天投入，换来的是 B4、B5 全部产出的地基。

**② 权限与安全 —— 现在完全空白**

- MCP server 无鉴权（D-035 已记录）
- 无提示注入防护（用户输入里塞"忽略以上指令"）
- 无审计日志（谁在什么时候查了哪份合同）

**法务场景尤其致命** —— JD4 写的是"金融 / 法律等场景"，这些场景**合规是硬门槛**。

**③ 幂等 / 重放**

现在全只读，不痛。但一旦加写操作（导出报告、提交审核），**重放必须幂等**。

好消息：你在 Milvus 那一层已经见过同类问题（`upsert` = 墓碑 + 插入，D-020）。

## 四、差距三分法（别全补）

### A 类｜必须补 —— 面试会问，项目也需要

| 项 | 何时 | 成本 |
| --- | --- | --- |
| **eval 集 + 断言脚本** | **B4-0（已插入）** | 半天 |
| 降级实验（3 个） | B4-1 ~ B4-3 | 1 天 |
| 可观测性 + 成本数据 | B5 | 1 天 |

### B 类｜知道即可 —— 能讲清取舍，不必实现

| 项 | 怎么讲 |
| --- | --- |
| 权限 / 多租户 | "MCP 把能力标准化了，也把**暴露面**标准化了；生产要在 tool 层按 `doc_id` 过滤" |
| 提示注入 | "把系统指令和用户输入分层，工具返回视为不可信数据，不当作指令执行" |
| 幂等重放 | "写操作用幂等键，不依赖副作用可重试" |
| 模型分级 | "简单路由用小模型，复杂推理用大模型" |
| Plan-and-Execute | 用"7 次打转"的实测数据讲动机 |

### C 类｜岗位不需要

- 大规模分布式编排（平台团队的事）
- 多模态 Agent
- 自研推理引擎 / 微调 Agent 模型

## 六、面试时怎么讲（正向包装 + 诚实边界）

**不要自称"精通 Agent"。** 更好的说法是给出边界：

> "我在一个真实合同审查场景里把 Agent 从零做到了能跑：
> 手写 ReAct 和 LangGraph 各实现一遍，把工具选择、循环收敛、HITL 都做了实测。
> 我最清楚的其实不是它多强，而是**它在什么情况下会失效** ——
> 我记录了 14 组实验，包括工具输出缺字段导致它反复反问、字段含义混用导致人工无法判断风险等级。
>
> 我也清楚自己的短板：**我还没有 eval 集，所以"改完更好"目前只能靠个案判断，不能量化。**
> 这是我下一步要补的。"

**为什么这样说更好**：

- 有边界感的人更像工程师
- 主动说出短板，比被问出来强
- **"我知道我缺什么"本身就是能力**

## 七、一句话定位

> **现在是"能做出功能正确的 Agent"，还不是"能运营一个 Agent 产品"。**
>
> 差的那一半不是技术难度，是**工程纪律**：
> 没有 eval 就不知道好坏，没有 trace 就不知道慢在哪，没有权限就不敢上生产。

**而这三点里，你已经具备实现它们的能力了** ——
你有 14 条实验记录的习惯，eval 只是把这个习惯自动化。
