## D-001｜`chunk_id` 用内容哈希而不是自增 ID

**决策**

```python
raw = f"{doc_id}|{char_start}|{clause_no or ''}|{index}/{total}|{text}"
chunk_id = hashlib.sha1(raw.encode("utf-8")).hexdigest()[:16]
```

**为什么**

- **确定性**：同一份合同重复上传 → 得到相同的 ID
- 配合 Milvus 的 `upsert` → **天然幂等**，不需要另写去重逻辑（W3 Day 19）
- 主键里**必须含 `char_start`**：真实合同里同一段条款文本会出现多次
  （附件重排、末页错位），不含位置信息就会碰撞

**反过来会怎样**

- 用 `uuid4`：每传一次就多一份副本，W3 的幂等要另想办法
- **去掉 `char_start`**：Day 3 用真实合同实测 —— 78 个块只剩 **76 个唯一 ID**，
  两处碰撞。被覆盖的两块文本相同，但 `page` / `char_start` 不同，
  结果 **引用会指向错误的位置**，而且**不会报任何错**

**来源**：Day 3 `app/core/chunker.py` 的 `_make_chunk_id`；Day 4 用真实合同确认

**面试怎么用**

问「重复上传同一份文件会不会产生脏数据」时，这是完整答案。

加分点在于能说清**为什么 ID 里必须有位置信息** ——
大多数人只会说"我用内容哈希"，但说不出"为什么纯内容哈希不够"。

## D-010｜归一化让内积等价于余弦

**决策**：编码时就 `normalize_embeddings=True`，
于是 Milvus 的稠密索引可以用 `metric_type="IP"`。

**为什么**

```
归一化后 |a| = |b| = 1

IP(a, b)     = a · b
COSINE(a, b) = (a · b) / (|a| × |b|)
             = (a · b) / (1 × 1)
             = a · b          ← 与 IP 完全相等
```

**省掉的**：COSINE 每次都要先算两次模长、再做一次除法。
候选数量大时，这是一笔纯粹的浪费。

**反过来会怎样**

- **不归一化却用 `IP`** → 分数**受向量模长影响**，
  长文本的块天然得分更高 → **排序被长度污染，而不是被语义决定**
- 将来换 embedding 模型时，如果新模型不做归一化 →
  **必须同时改 `metric_type`**，否则静默出错

**来源**：Day 2 `app/core/model_runtime.py::_encode_sync`；
Day 4 `vector_store._build_index_params`

**面试怎么用**：**高频题** —— "向量检索为什么可以用内积代替余弦"。
完整答法 = 归一化 + 数学等价 + 省掉的计算 + 不这么做会怎样。

> ⚠️ 位置要说**函数名 `_encode_sync`**，不要说"第 89 行"。
> 行号改几行代码就变了，面试里说行号既不专业也经不起追问。

## D-017｜`index_type` 和 `metric_type` 是两个不同的东西

**决策**

```python
index_params.add_index(
    field_name="sparse",
    index_type="SPARSE_INVERTED_INDEX",   # 用什么数据结构存
    metric_type="BM25",                   # 怎么算相似度
)
```

**为什么**

两个参数回答的是不同的问题：

| 参数 | 回答 | 取值来源 |
| --- | --- | --- |
| `index_type` | **用什么数据结构存** | 向量 / 稀疏矩阵的索引结构 |
| `metric_type` | **怎么算相似度** | 距离或评分函数 |

`BM25` 只是一个**评分函数**，不是一种索引结构。
稀疏向量的倒排索引类型名是 `SPARSE_INVERTED_INDEX`。

**反过来会怎样**

- 把 `BM25` 填进 `index_type` → **`create_collection` 直接失败**，后面几步全跑不了
- 稀疏索引的 `metric_type` 若不是 `BM25` → **Function 白建**：
  稀疏向量里存的是 **BM25 词权重**，只有 BM25 打分器知道怎么解读
  （它需要文档频率、平均文档长度这些统计量）

**一个额外发现**：索引类型名是**原样透传给服务端的字符串**。
实测：在 pymilvus 源码里搜 `SPARSE_INVERTED_INDEX` / `HNSW` / `IVF_FLAT` —— **全部无匹配**。
意味着本地没有校验、没有自动补全，**拼错了要连上 Milvus 才报错**。

**来源**：Day 4 `app/core/vector_store.py::_build_index_params`（连填错两次后修正）

**面试怎么用**：问"稀疏检索用什么索引"或"Milvus 索引配置有哪些参数"时，
能讲清 `index_type` 与 `metric_type` 的分工就是满分答案。

## D-018｜`or` 做 None 合并对整数是错的

**决策**

```python
"page": chunk.page if chunk.page is not None else _NO_PAGE   # ✅
"page": chunk.page or _NO_PAGE                                # ❌
```

**为什么**

`or` 判断的是**真假值**，不是**是否为 None**。
而 `0` 在 Python 里是假值 —— 所以 `0 or -1` 会得到 `-1`。

**反过来会怎样**

- 实测 `page` 取值 `[2, 3, 5, 7, 8, 9, 10, 12]` —— **从 1 开始**
  （`parser.py` 用 `enumerate(pages, start=1)`），所以当前**踩不到**
- **但 `char_start` 可以是 0**（前言块的 `char_start=0`）。
  若对它用 `or`，位置信息会直接错掉
- 所以这个写法是「**碰巧正确**」，不是「正确」

**来源**：Day 4 `_chunk_to_row`。
当时三处**字符串**字段被改了，唯独唯一有风险的 **`page`** 漏了 ——
因为改动是照着"字符串那几行"做的，不是照着"`or` 对整数不安全"这个问题类别做的。

**面试怎么用**：不直接考。但"怎么识别一个碰巧能跑的写法"是代码质量讨论里的加分点。

## D-019｜`max_length` 给小了是报错，不是截断

**决策**：建表前**实测**各 VARCHAR 字段的实际最大长度，再定 `max_length`。

**为什么**

Milvus 的 VARCHAR 超出 `max_length` 会**拒绝写入并抛错**。
所以这个值既不能凭感觉给，也不能一律 `65535`（那样就失去了约束意义）。

**反过来会怎样**

- 给小了 → **运行时插入失败**（好在不静默，不会悄悄丢字）
- 给大了 → 没有实际代价，但等于没约束

Day 4 实测（2 份真实合同 + 1 份合成 fixture）：

| 字段 | 实测最长 | 声明 | 余量 |
| --- | --- | --- | --- |
| `clause_no` | 5（`第二十一条`） | 64 | 12× |
| `clause_title` | 18（`因不可抗力或者已尽合理注意义务仍不能`） | 64 | 3.5× |
| `section` | 13（`第三章 合同双方的权利义务`） | 64 | 5× |

**来源**：Day 4 TODO-1 review（`max_length=64` 的选择经验证成立）

**面试怎么用**：问"你怎么定 VARCHAR 的 max_length"时，
答"建表前跑了实测"比"给了个够大的值"有说服力。

## D-020｜Milvus 的 upsert = 墓碑 + 插入，所以 `row_count` 会虚高

**决策**

- 断言幂等性用 `query(filter="", output_fields=["count(*)"])`
- **不用** `get_collection_stats().row_count`

**为什么**

Milvus 的存储是**只追加**的：segment 一旦落盘就**不可变**，所以**没有原地更新**。

```
upsert 的真实动作 = 写一条删除标记（墓碑）+ 写入新行
```

- **查询**会过滤墓碑 → `count(*)` 得到真实值
- **`get_collection_stats`** 不过滤墓碑 → 统计值虚高
- 墓碑要等 **compaction**（后台段合并）才被物理清除

**反过来会怎样**

Day 4 实测：同一份文档写 3 次

| | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 统计值 | 10 | 20 | **30** |
| 真实可查询 | 10 | 10 | **10** |

**用统计值做断言 → 一个完全正确的 upsert 被判为失败。**
Day 4 实际发生了：验收报 ❌，害得去怀疑自己的实现。

**来源**：Day 4 `scripts/milvus_smoke.py` 第 3 步 + `vector_store.count_rows()`

**面试怎么用**：问"Milvus 的删除 / 更新是怎么实现的"——
标准答案就是**只追加 + 墓碑 + 查询时过滤 + compaction 回收**。

## D-021｜VARCHAR 主键在搜索结果里的键名是字段名，不是 `id`

**决策**

```python
chunk_id=str(item.get("chunk_id") or item.get("id") or "")
```

**为什么**

Milvus 搜索结果里，**主键的位置随主键类型变化**：

| 主键类型 | 结果里的键名 |
| --- | --- |
| **VARCHAR**（我们的 `chunk_id`） | **字段名本身**，在 hit 的顶层 |
| INT64 自增 | 通用键 `id` |

实测的 hit 结构：`keys = ['chunk_id', 'distance', 'entity']`

**反过来会怎样**

- 只读 `item["id"]` → 拿到**空字符串**，**而且不报错**
- 后果：`SearchHit.chunk_id` 全程为空 → **引用无法回溯** → 没有任何异常提示
- Day 4 实际发生：验收输出的示例是 `chunk_id=`（空的），
  是人工看出来的，不是程序报出来的

**来源**：Day 4 实测（`_to_hits` 由我写错）

**面试怎么用**：属于"**静默失败**"类经验 ——
不抛异常、不报错，只是悄悄给你一个空值。讲调试故事时很有用。

## D-022｜RRF 的分数尺度和单路完全不同

**决策**：混合检索用 `RRFRanker(k=60)`，**不**把两路分数加权求和。

**为什么**

```
RRF: score(d) = Σ 1 / (k + rank_i(d))
```

它**只用排名，不用原始分数** —— 所以对量纲不敏感。

**反过来会怎样**

Day 4 实测的分数范围：

| 路径 | 分数范围 |
| --- | --- |
| `dense` | 0.29 ~ 0.54 |
| `bm25` | 0.59 ~ **7.58** |
| `hybrid` | 0.032 ~ 0.033 |

- **直接相加** → BM25 那一路单方面说了算（7.58 对 0.54），
  向量检索的结果等于被淹没了
- RRF 的量级：`#1 名 = 1/(60+1) ≈ 0.0164`，**两路都排第一 ≈ 0.0328**
  （实测 hybrid top1 = 0.0328 正是这个含义）

**来源**：Day 4 `milvus_smoke.py` 实测输出

**面试怎么用**：问"混合检索怎么融合两路结果"时，这是完整答案。
能报出实测的分数范围，比只说"用 RRF"强得多。

## D-024｜重试只包单次 HTTP 调用，不包流式消费

**决策**：`_create_with_retry()` 只包 `chat.completions.create()` 这一句。
`stream()` 里消费流的 `async for` **故意留在重试范围之外**。

**为什么**

流已经 `yield` 给调用方的内容**收不回来**。重试整个生成器 =
用户看到前半段文字重复输出两遍。

正确的边界是：**重试只覆盖"还没吐出任何内容"的阶段。**

```
create() 失败        -> 还没吐字，安全重试          ✅
开始 yield 之后失败   -> 已经吐了，重试 = 重复输出   ❌ 直接抛错
```

因为重试恰好只包 `create()`，这个边界**自动成立**，不需要额外判断。

**重试策略的两个判断**

| 异常 | 重试 | 理由 |
| --- | --- | --- |
| `APIConnectionError` / `APITimeoutError` | ✅ | 瞬时网络问题 |
| `RateLimitError`（429） | ✅ | 加退避等待 |
| `APIStatusError` 且 `status_code >= 500` | ✅ | 服务端瞬时故障 |
| 401 / 400 | ❌ | **确定性失败** —— 重试不会改变错误的输入 |

> ⚠️ 5xx 要用 `status_code >= 500` 判断，**不要枚举**。
> 枚举很容易漏 —— 第一版漏掉了 **502**，而 502 恰恰是网关/代理层最常见的瞬时错误。

**反过来会怎样**

- 包住整个生成器 → 重试时前半段文字重复输出
- 枚举 5xx 而漏掉 502 → 网关抖动时请求直接失败，明明重试就能过
- 重试 401/400 → 浪费配额与时间，且把"输入有错"这个信息延迟暴露

**附带实现细节**：tenacity 的 `with attempt:` 对**不可重试的异常也先抑制**，
真正的判定发生在下一轮 `iter()`。所以计数器放在 `with` 之后也能数到每一次尝试
（实测：3 次尝试 → 计数 2 次重试；401 首次失败 → 计数 0 次重试）。

**来源**：Day 5 TODO-4（`app/core/llm.py`）

**面试怎么用**：问"流式接口怎么加重试"—— 标准答案就是这个边界划分。

## D-025｜材料标识与定位信息必须分开

**决策**：材料排版成

```
[a3f7d2b5a00c4596] 来源：第七章 研学旅游协议条款 · 第二十六条 · 合同生效 页码：25
第二十六条 合同生效
本合同一式 份，……
```

**标识独立成一个方括号，定位信息放在括号外。**

**为什么**

这两样东西的服务对象不同：

| | 标识 | 定位 |
| --- | --- | --- |
| 给谁用 | **机器 / 校验器** | **人 / 模型** |
| 要求 | 全局唯一、短、**模型必须精确复现** | 可读、帮模型说清"依据在哪" |
| 要不要模型抄 | **要** | **不要** |

**混在同一个括号里会出两个问题**：

1. 模型引用时得把章节、条款、标题、页码**全抄一遍** —— 抄错一个字就核对不上
2. 校验器**抓不到** —— 实测第一版写成 `[来源: id 章节 条款 标题 页码]`，
   校验器报「材料里出现的标识: **0 个**」，因为它期望方括号里只有一个 ID

**标识为什么用 `chunk_id` 而不是 `clause_no`**

`clause_no` **会重复** —— 附件里也有"第一条"，
实测那份养老合同里"第一条"出现了**两次**。只有 `chunk_id` 是全局唯一的。

**反过来会怎样**

- 标识和定位混一起 → 引用极易抄错，且校验器失效
- 用 `clause_no` 当标识 → 引用指向不唯一，核对等于没做

**来源**：Day 5 TODO-2（`app/core/rag.py::_format_context`）

**面试怎么用**：问"RAG 的引用怎么做才能核对"时，
"标识与定位分离"是那个能显出设计功力的点。

## D-026｜低温管随机性，不管编造

**决策**：`temperature=0.1` **之外**，提示词里仍然显式写
「只能依据材料回答，材料中没有相关内容就说'材料中无相关内容，无法回答'」。

**为什么**

| `temperature` 管什么 | 不管什么 |
| --- | --- |
| **采样随机性** —— 让模型在候选里更倾向高分项 | **编造** |

**幻觉不是随机性问题，是指令遵循问题。** 温度调到 0，
模型照样会自信地编一个"材料里没有、但听起来合理"的答案。

所以这两件事**必须分开做**：

- 低温 → 减少同一个问题两次回答不一致
- 约束 → 防止模型说材料里没有的事

**反过来会怎样**

- 以为低温就够 → 问一个材料里没写的问题（比如"违约金是多少"），
  会得到一个**编造的数字**，而且看起来很可信
- 这正是法务场景最危险的失败模式：**错误 + 自信**

**来源**：Day 5 TODO-3（`app/core/rag.py::SYSTEM_PROMPT`）

**面试怎么用**：问"审查类任务的 temperature 怎么设"时，
只答"设低温求确定性"是及格；
**补上"但低温不防幻觉，防幻觉靠约束"才是满分**。

## D-027｜引用核对必须同时查"编造"和"没引用"

**决策**：验收脚本同时核对**条款号**和**材料标识**，
并把「回答里一个标识都没有」判为**失败**。

**为什么**

一个只核对"编造的引用"的检查，会有**假阳性**：

```python
cited = set(re.findall(r"第[一二三四五六七八九十百零〇\d]+条", answer))
unknown = cited - hit_clauses
return 1 if unknown else 0          # ← 空集减空集 = 空集 -> 返回 0，通过
```

**如果模型一个引用都不写**：`cited` 是空集 → `unknown` 也是空集 →
**判定通过**。一个完全不引用、全靠编的回答会被判为合格。

**这个失败模式比漏检更危险**：漏检至少还显示"没查到"，
假阳性会给你一个 ✅，让你以为链路是好的。

**反过来会怎样**

- 只查编造 → 模型无视引用要求时，校验器报 ✅
- 只查条款号、不查标识 → 模型编一个假标识（`[deadbeef12345678]`）也发现不了

**设计上的一步**：标识的正则定义放在 `rag.py`，
**和生成它的 `_format_context` 放在一起**。分开定义的话，
将来改了格式而忘了改校验器，校验器**不会报错**，
只会安静地告诉你"没有引用" —— 又是一次静默失效。

**来源**：Day 5 校验器加强（`scripts/rag_demo.py`）

**面试怎么用**：属于"**怎么保证你的评估本身可信**"这一类问题。
能讲出"检查本身也会有假阳性"，是评测意识的体现。

## D-028｜`to_thread` 买的是并发响应性，不是单请求速度

**决策**：`chunk_document` / `parse_document` 一律 `await asyncio.to_thread(...)`，
与 `model_runtime` / `vector_store` 保持一致。

**为什么**

同步阻塞调用跑在 `async def` 里，会**冻住整个事件循环** ——
期间所有请求都不能被处理，并发能力归零。

实测（`scripts/blocking_probe.py`，50 页 PDF，解析约 1.5s）：

| | 轻任务调度延迟 | 重任务自身耗时 |
| --- | --- | --- |
| 直接在事件循环里 | **1519.1 ms** | 1519.2 ms |
| `asyncio.to_thread` | **0.1 ms** | 1477.4 ms |

**轻任务被拖慢约 13000 倍；而重任务自己几乎没变（差 3%）。**

**反过来会怎样**

- **用单请求测这个改动，一定得出"没有区别"** —— 因为改的本来就不是它的耗时。
  这是最容易被误判为"改动无效"的地方。
- 不丢线程池 → 一次上传会让所有人的提问卡住 1.5 秒以上

**边界（容易答漏的一半）**

| | `to_thread` 的效果 |
| --- | --- |
| 并发**响应性** | ✅ 大幅改善 |
| **吞吐量**（CPU 密集部分） | ❌ 不变 —— GIL 让线程的 CPU 工作仍然串行 |

**推论**：想要真正的 CPU 并行要用**进程**（多 worker），不是线程。
`to_thread` 只保住响应性，没给算力。

**判据**：多慢才值得丢线程池？`to_thread` 自己有几微秒开销。
实测 `parse_document` ≈ 1500ms（必须丢）；`chunk_document` ≈ 几毫秒（丢不丢都行，为一致性丢了）。

**来源**：Day 6 TODO-1（`app/core/ingest.py`、`app/api/v1/documents.py`）

**面试怎么用**：问"FastAPI 里怎么处理 CPU 密集任务"时，
能讲出"线程保响应性、进程要吞吐"这一组区分，而不是笼统说"用线程池"。

## D-029｜"检索为空"不等于"没有可用依据"

**决策**：`grounded` 由**回答是否引用了材料**决定，而不是由**检索是否返回结果**决定。

```python
grounded = bool(citations) and "无法回答" not in result.answer
```

**为什么**

第一版写的是 `if not result.hits: grounded = False`。**这几乎是死代码** ——
稠密检索**永远返回 top-k**，`result.hits` 只有在集合为空时才会是空的。

真正的信号在**回答**里：模型有没有给出可核对的结论。

**这个 bug 只有跑起来才看得见**

验收脚本对一个知识库里没有的问题发问，返回：

```
200  {"answer":"结论：材料中无相关内容，无法回答。\n\n依据：\n- 第二十四条 ... [936...]"}
```

**模型拒绝了，却照样给出了一条"依据"** —— 因为提示词的输出格式
强制它永远填一段「依据」。于是：

- `citations` 非空
- `grounded` 保持 `True`
- "无依据率"这个指标**永远不会触发**

单看 `query.py` 没问题，单看 `SYSTEM_PROMPT` 也没问题，**合起来就错了**。

**反过来会怎样**

- 用"检索为空"判断 → 该分支基本不执行，"答不上来"完全隐形
- 只改代码不提示词 → 模型继续在拒绝时硬填依据，`grounded` 仍不可信
- 所以修复必须**两边一起动**：提示词加「材料不足时只输出一行『无法回答』，不要写依据段」，
  代码才有一个可靠信号可读

**来源**：Day 6（`app/core/rag.py::SYSTEM_PROMPT` + `app/api/v1/query.py`）

**面试怎么用**：属于"**跨层契约**"类问题 ——
一个字段的语义，取决于上下游是否按同一个假设工作。

## D-030｜对外契约与内部模型必须分开

**决策**：`app/api/v1/schemas.py` 独立于 `app/core/schemas.py`。
`Citation` 不复用 `SearchHit`。

**为什么**

两者生命周期不同：

| | 内部模型（`SearchHit`） | 对外契约（`Citation`） |
| --- | --- | --- |
| 谁在用 | 检索、编排、评测 | 前端、第三方、SDK |
| 改动影响 | 内部重构 | **破坏调用方** |
| 字段 | 11 个（含 score / char_start / char_end） | 4 个（用户真正需要的） |

**照搬内部模型会怎样**：对外契约被内部实现绑死 ——
以后改检索层（比如 `section` 拆成 `chapter` + `section`）就得升接口版本。

**三个具体决定**

1. **`chunk_id` 必须暴露**（约定 5）—— 不给 ID，前端就没法把引用定位回条目
2. **字段名用对外名**（`clause_location` / `original_text`），不用内部名 ——
   内部改名时接口不用动
3. **`original_text` 给全文，不截断** —— 用途是"核对"，截断就核不了。
   真要限体积应该**限条数**（只给回答实际引用的那几条），不要限单条长度

**反过来会怎样**

- 直接 `return SearchHit` → 契约泄露内部字段，且内部一改就破坏调用方
- 截断 `original_text` → 用户无法判断原话有没有被曲解，"可核对"变成空话

**来源**：Day 6 TODO-2（`app/api/v1/schemas.py`）

**面试怎么用**：问"API 响应模型怎么设计"时，
"内外分离 + 只暴露用户需要的字段"是标准答案的核心。

## D-031｜冷启动开销必须在 lifespan 付掉

**决策**：`main.py` 的 lifespan 里预热**三样**：
本地模型、Milvus 连接、tiktoken 词表。

**为什么**

每一样都只在**第一次**付，但付的时候恰好是**第一个真实请求**：

| 冷启动项 | 实测 | 不预热的后果 |
| --- | --- | --- |
| Milvus 首次建连 | **4.1 s** | 第一个上传请求多等 4 秒 |
| tiktoken 词表加载 | **2.4 s** | 第一个提问请求多等 2.4 秒 |
| 本地模型加载 | 1.3 s | （Day 2 已经预热了） |

**怎么发现的 tiktoken 那一笔**

分段耗时对不上账：

```
total_ms  5871.1
segments  retrieve 213.5 + llm 3223.6 = 3437.1
未计入    2434 ms          ← 没有任何 span 覆盖
```

嫌疑落在 `count_messages_tokens()` 上（它内部 `tiktoken.get_encoding`）。
挪进 lifespan 后重测：

```
total_ms  2934.7 ；segments 合计 2933.4 ；未计入 1.3 ms
```

**2434 ms → 1.3 ms，假设被证实。**

**反过来会怎样**

- 不预热 → 每个 worker 的第一个请求都慢几秒，且**用户会以为是服务本身慢**
- 不打点 → 这笔开销**完全隐形**，"总耗时 5871 但各段加起来 3437"这种账
  不主动对账就永远看不见

**两条分界线**

| 项 | 放哪 | 为什么 |
| --- | --- | --- |
| Milvus 连接 | **fail-fast 的 try 里** | 它是核心依赖，连不上就不该对外提供服务 |
| tiktoken | **try 外面** | 加载失败不致命，`count_tokens` 会退化为按字符估算，不该因此拒绝启动 |

**来源**：Day 6（`app/main.py` lifespan）

**面试怎么用**：问"服务刚启动时第一个请求为什么慢"——
能报出具体毫秒数并说明"已挪进预热"，比说"有冷启动问题"强得多。
