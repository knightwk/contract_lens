## D-001｜`chunk_id` 用内容哈希而不是自增 ID

**决策**

```python
raw = f"{doc_id}|{char_start}|{clause_no or ''}|{index}/{total}|{text}"
chunk_id = hashlib.sha1(raw.encode("utf-8")).hexdigest()[:16]
```

**为什么**

- **确定性**：同一份合同重复上传 → 得到相同的 ID
- 配合 Milvus 的 `upsert` → **天然幂等**，不需要另写去重逻辑（W3 Day 19）
- 主键里**必须含 `char_start`**：真实合同里同一段条款文本会出现多次
  （附件重排、末页错位），不含位置信息就会碰撞

**反过来会怎样**

- 用 `uuid4`：每传一次就多一份副本，W3 的幂等要另想办法
- **去掉 `char_start`**：Day 3 用真实合同实测 —— 78 个块只剩 **76 个唯一 ID**，
  两处碰撞。被覆盖的两块文本相同，但 `page` / `char_start` 不同，
  结果 **引用会指向错误的位置**，而且**不会报任何错**

**来源**：Day 3 `app/core/chunker.py` 的 `_make_chunk_id`；Day 4 用真实合同确认

**面试怎么用**

问「重复上传同一份文件会不会产生脏数据」时，这是完整答案。

加分点在于能说清**为什么 ID 里必须有位置信息** ——
大多数人只会说"我用内容哈希"，但说不出"为什么纯内容哈希不够"。

## D-002｜配置大小写：`case_sensitive=True` 会让 `.env` 静默失效

**决策**：`Settings` 配 `case_sensitive=False`。

**为什么**

`.env` 里的变量名按惯例是**大写**（`MILVUS_URI`），而 pydantic 字段名是**小写**（`milvus_uri`）。
开 `case_sensitive=True` 时两者对不上 → 字段读不到 → 退回默认值。

**反过来会怎样（这题真正的答案）**

**它不会让服务起不来。** 每个字段都有默认值，pydantic 不报错 ——
服务照常启动，只是**用的是默认配置，不是你在 `.env` 里写的**。

| | 崩溃 | 静默退回默认值 |
| --- | --- | --- |
| 什么时候发现 | 立刻 | **可能永远发现不了** |
| 本地 vs 生产 | 都崩，立刻暴露 | 本地默认值恰好对，**生产才炸** |

> 所以正确答案不是"起不来"，而是 **"起来了，但你不知道它读的是哪份配置"**。

**怎么防**：`/health` 把生效的关键配置打出来 —— 一眼看出是不是你填的那份。

**来源**：Day 1 `app/config.py`

**面试怎么用**：配置错误怎么尽早暴露。"静默退回默认值比崩溃更难查"是好答案。

## D-004｜相对路径会在不同启动上下文下静默失效

**决策**：所有路径从 `PROJECT_ROOT` 派生，不用 `Path("./models")` 这种相对 CWD 的写法。

**为什么**

`"./models"` 的正确性**取决于进程从哪里启动**：

| 启动方式 | CWD | `./models` 指向 |
| --- | --- | --- |
| `uvicorn app.main:app`（仓库根） | 仓库根 | ✅ |
| `python scripts/xxx.py` | 仓库根 | ✅ |
| **从别的目录调用** | 任意 | ❌ 找不到，或建出空目录 |
| Docker `WORKDIR /app` | /app | ✅（靠巧合） |

**反过来会怎样**

- 失败表现是 **`FileNotFoundError`，或者更糟 —— 静默建出一个空 `models/` 目录**，
  然后在完全无关的地方报"模型加载失败"
- 而**它在本机的常规开发方式下永远是对的** → 这个 bug 会一路活到部署

**判据**：凡是"从某处读文件"的路径，都必须能追溯到**一个明确的根**。

**来源**：Day 1 `app/config.py` 的 `PROJECT_ROOT` / `_resolve_model_path`

**面试怎么用**：答"避免依赖启动目录"比"更规范"具体得多。

## D-005｜`/health` 不放在 `/api/v1` 下

**决策**：`/health` 挂根路径，业务接口挂 `/api/v1`。

**为什么**

**判据：这个接口会随业务版本演进吗？谁在调用它？**

`/health` 的调用方是 **K8s 探针、负载均衡、Docker healthcheck** ——
它们写死在**部署配置**里，不跟着你的 API 版本走。

**反过来会怎样**

- 若放在 `/api/v1` 下 → 出 v2 时你要么**在 v2 里再放一份一模一样的 `/health`**，
  要么改所有部署配置
- 更糟：探针失效会让 **K8s 把健康的 Pod 判成不健康并重启** ——
  为了一个纯基础设施端点引发滚动重启

**判据提炼**：**"谁在调用它"决定它要不要版本化。**
人/前端调用的业务接口 → 版本化；基础设施调用的探针接口 → 不版本化。

**来源**：Day 1 `app/api/health.py`、`app/main.py`

**面试怎么用**：能说出"不是所有接口都该版本化"，比只会写 `/v1` 强一层。

## D-006｜Provider 开关用 `Literal` 而非 `str`

**决策**：`embedding_provider: Literal["local", "api"]`，不是 `str`。

**为什么**

用 `str` 时，`EMBEDDING_PROVIDER=lcocal`（打错一个字母）**照样能启动**，
然后走进一个没人写过的分支，或在 `if` 里静默落空。

用 `Literal`，**pydantic 在加载配置时就抛校验错**，服务根本起不来。

**反过来会怎样**

| | `str` | `Literal` |
| --- | --- | --- |
| 拼错时 | 启动成功 | **启动失败** |
| 何时发现 | 第一个请求，或永远不 | 启动时 |
| 排查成本 | 高（现象在别处） | 零（错误直指字段） |

**本质：把运行时的错误提前到启动时。**
配置错误的代价和发现时间成正比 —— 越早越便宜。

**来源**：Day 1 `app/config.py`

**面试怎么用**：属于"怎么让错误尽早暴露"。`Literal`/`Enum` 替 `str` 是标准做法。

## D-007｜`torch.set_num_threads` 必须放 `__init__`，不能放 `warmup`

**决策**：在模型加载**之前**设线程数。

**为什么**

`torch.set_num_threads()` 影响的是 **torch 内部线程池的创建参数**。
线程池在**第一次做运算时**才真正建起来 —— 之后改这个值**不会重建已存在的池**。

放 `warmup` 里就晚了：`warmup` 本身要先加载模型并跑一次推理，
**那一次推理已经按默认值把线程池建好了**。

**反过来会怎样**

- **不报错、不警告，就是没生效** —— 你设了 4，实际跑的是默认（可能等于核数）
- 表现是 CPU 打满、单次推理变慢、并发互相拖累，而你看代码觉得"我明明设了"
- 这类"**设晚了**"的问题在本项目里出现多次，共同点是**生效时机**而不是取值对错

**判据**：配置一个会被**惰性创建**的东西时，要问"它什么时候第一次被创建"，
而不是"我什么时候想起来设它"。

**来源**：Day 2 `app/core/model_runtime.py`

**面试怎么用**：问"本地模型怎么调优 CPU 推理"时，
"线程数必须在首次推理前设"比"设成 4"有含量。

## D-008｜`asyncio.to_thread` 之外还要加信号量

**决策**：`to_thread` 外面再套 `asyncio.Semaphore(MAX_CONCURRENT_INFERENCE)`。

**为什么**

`asyncio.to_thread` 用的是**默认线程池**，`max_workers` 是 `min(32, cpu_count + 4)` ——
**这个数字和"模型能吃多少并发"毫无关系**。

`to_thread` 只保证"不阻塞事件循环"，**不保证并发数受控**。

**反过来会怎样**

8 个并发请求 → 默认线程池可能开 8~12 个线程 → **十几份推理同时抢 CPU**：

| | 有信号量（=2） | 无信号量 |
| --- | --- | --- |
| 同时推理数 | 2 | 8~12 |
| 单请求延迟 | 可控 | **全部变慢**（互相抢核） |
| 内存峰值 | 可控 | 飙升（每份都有中间张量） |
| 总吞吐 | 可能更高 | **反而更低**（切换 + 缓存失效） |

**关键认知：并发度高不等于吞吐高。** CPU 密集任务超过核数只会互相拖累。

**来源**：Day 2 `app/core/model_runtime.py`

**面试怎么用**：问"本地模型怎么支撑并发"时，
"用信号量把并发压到核数量级"是完整答案。

## D-009｜信号量必须按事件循环惰性创建

**决策**：不用模块级 `asyncio.Semaphore(...)`，而是按当前事件循环惰性创建。

**为什么**

`asyncio.Semaphore`（以及 `Lock`、`Event`）在**第一次被 await 时绑定到当时的事件循环**。
之后换个循环再用 → `RuntimeError: ... is bound to a different event loop`。

**什么时候会出现第二个循环**

| 场景 | 说明 |
| --- | --- |
| **pytest 跑多个测试** | 每个 `asyncio.run()` 建一个新循环 |
| uvicorn `--reload` | 重载时可能重建 |
| 脚本里多次 `asyncio.run()` | 每次一个新循环 |

**反过来会怎样**

- 模块级创建 → 在测试里大概率炸，而且**报错指向 semaphore，根因却是"循环换了"**
- 更麻烦的是**时好时坏**：单跑一个测试通过，跑全部就挂

**做法**：把 `{事件循环: semaphore}` 存起来，取的时候按当前循环查/建。
多几行代码，换**任何启动方式下都能工作**。

**来源**：Day 2 `app/core/model_runtime.py` 的 `_semaphore()`

**面试怎么用**：属于"只有测试环境才暴露的问题"。能讲出 asyncio 原语绑定事件循环的机制就够了。

## D-010｜归一化让内积等价于余弦

**决策**：编码时就 `normalize_embeddings=True`，
于是 Milvus 的稠密索引可以用 `metric_type="IP"`。

**为什么**

```
归一化后 |a| = |b| = 1

IP(a, b)     = a · b
COSINE(a, b) = (a · b) / (|a| × |b|)
             = (a · b) / (1 × 1)
             = a · b          ← 与 IP 完全相等
```

**省掉的**：COSINE 每次都要先算两次模长、再做一次除法。
候选数量大时，这是一笔纯粹的浪费。

**反过来会怎样**

- **不归一化却用 `IP`** → 分数**受向量模长影响**，
  长文本的块天然得分更高 → **排序被长度污染，而不是被语义决定**
- 将来换 embedding 模型时，如果新模型不做归一化 →
  **必须同时改 `metric_type`**，否则静默出错

**来源**：Day 2 `app/core/model_runtime.py::_encode_sync`；
Day 4 `vector_store._build_index_params`

**面试怎么用**：**高频题** —— "向量检索为什么可以用内积代替余弦"。
完整答法 = 归一化 + 数学等价 + 省掉的计算 + 不这么做会怎样。

> ⚠️ 位置要说**函数名 `_encode_sync`**，不要说"第 89 行"。
> 行号改几行代码就变了，面试里说行号既不专业也经不起追问。

## D-011｜切块计数用 BGE 自己的 tokenizer，不用 tiktoken

**决策**：`chunker.py` 用 BGE 的 tokenizer 数 token；只有算 LLM 上下文预算时才用 tiktoken。

**为什么**

要回答的问题是：**这个块塞进 embedding 模型会不会被截断？**
决定这件事的是**模型自己的 tokenizer**，不是 tiktoken 的词表。

BGE 的 `max_seq_length=512` 是按它自己词表算的。用 tiktoken 数出来的"500"，
在 BGE 眼里可能是 600 —— 于是你按 400 字切块，编码时**静默截断**，后半段根本没进向量。

**反过来会怎样（有实测）**

EXP-005 测过：同一段中文 tiktoken 比 DeepSeek 真实 tokenizer **多算 1.62 倍**。
换到 BGE 上偏差方向可能相反 —— **两个词表之间的偏差没有固定关系**。

> **用 A 的词表去保障 B 的窗口，等于没保障。**

**分工**

| 场景 | 用哪个 | 为什么 |
| --- | --- | --- |
| 切块（喂 embedding 模型） | **BGE tokenizer** | 被截断的是它 |
| 上下文预算（喂 LLM） | tiktoken 估算 | 只能估，真值以 API usage 为准 |

**来源**：Day 3 `app/core/chunker.py`

**面试怎么用**：问"chunk size 怎么定"时，指出"要用目标模型自己的 tokenizer 数"，
比背"512 token"强得多。

## D-012｜条款正则必须行首锚定

**决策**：`_RE_CLAUSE` 等全部用 `^` 锚定行首。

**为什么**

合同正文里到处是**交叉引用**：「甲方未按本合同第四条约定的期限支付款项的……」。
不加 `^`，`第四条` 会被当成**新条款的开头**，一个句子被切成两半，
后半段挂到一个不存在的"第四条"上。

**反过来会怎样**

- 切分错误**完全静默** —— 不报错，只是块变多、内容错位
- 更糟：`chunk_id` 里含 `char_start`，切错会让**同一份文档二次入库得到不同 id**，
  幂等性直接失效（D-001 修 `chunk_id` 时踩过）

**判据**：结构化文本（合同 / 法条 / 日志）的**边界识别必须锚定位置**，
因为同样的字在正文里会作为**引用**出现。

**测试**：`tests/test_chunker.py` 的 `test_clause_set_is_exact`（集合相等，不是"包含"）
就是防这个 —— 多切出一个假条款，集合立刻不等。

**来源**：Day 3 `app/core/chunker.py`

**面试怎么用**：能举出「交叉引用」这个具体反例，最有说服力。

## D-013｜附件与签署区要独立成组，不能挂到最后一个条款

**决策**：用哨兵正则（`_RE_APPENDIX` / `_RE_BODY_END` / `_RE_SIGNATURE`）截断正文。

**为什么**

合同末尾有大量**非条款内容**：附件清单、签署页、联系人表格。
只认"下一个条款号"的切分逻辑，会把这些**全部挂到最后一个条款上**。

**反过来会怎样（实测）**

修复前，那份养老合同里 **「第十五条」吞掉 33/78 块，占 42%** ——
检索命中第十五条时，返回的可能是附件里的任何东西。

**为什么它比 `chunk_id` 碰撞更危险**

| | `chunk_id` 碰撞 | 尾块吞并 |
| --- | --- | --- |
| 表现 | 数据丢失（78 → 76 唯一） | **数据错位** |
| 发现难度 | 主动去重才看得见 | 检索照常返回，**结果看起来合理** |
| 后果 | 少了两块 | **引用指向错误的原文** |

**引用指向错误原文，对法务产品是致命的** —— 而且它不报错。

**为什么不能用"条款长度上限"兜底**

设一个长度上限去截断，会把「**长条款**」和「**条款 + 尾部垃圾**」当成同一件事：
真正的长条款被拦腰切开，尾部垃圾只是被挪到下一块。**混淆了两种不同的病。**

**来源**：Day 4（真实合同 P1 缺陷修复）

**面试怎么用**：这是本项目最有说服力的 bug 故事 ——
"检索看起来正常，但引用指错了地方"。

## D-014｜「跨页重复」启发式对页码无效

**决策**：页眉页脚用**模式匹配**（`_PAGE_NUMBER_PATTERNS`），不靠"跨页重复"。

**为什么**

常见做法是统计每页首行/末行，**跨页重复**的判为页眉页脚。
但页码是「第 1 页 共 50 页」「第 2 页 共 50 页」—— **每页都不一样**，
永远不满足"重复"这个条件。

**反过来会怎样（真实发生）**

Day 3 那份养老合同：页脚清理**一条都没命中**，每页页码都留在正文里被切进块：

- 条款里夹着 "14"、"15" 这种孤立数字
- 引用原文里混进页码，用户核对时看着奇怪
- 更隐蔽的：这些数字会干扰 BM25 的词频统计

**分类判据**

| 类型 | 例子 | 该用什么 |
| --- | --- | --- |
| **固定**页眉页脚 | 公司名、密级标记、文档标题 | 跨页重复统计 ✅ |
| **变化**页眉页脚 | 页码、日期、章节名 | **必须模式匹配** ✅ |

**判据**：**启发式的隐含假设，要对着真实数据验一遍。**
"跨页重复"假设了"页眉页脚内容固定"，而页码恰好违反它。

**来源**：Day 3 `app/core/parser.py`（真实合同 P2 缺陷）

**面试怎么用**：能讲出"启发式的假设在什么数据上不成立"，比说"用了启发式"强。

## D-015｜页码单调性自检的价值

**决策**：解析完顺手做一次页码审计（`_audit_pages`），结果写进 `meta`。

**为什么**

真实 PDF 有各种问题：**页码回退**（49 后面跟了个 1）、**整页无文本**（扫描页）。
它们不让解析失败，但会让**引用定位错位** —— 而引用定位是约定 5 的根基。

**反过来会怎样**

- 不自检 → 你会**无条件相信** `page` 字段，直到用户点开引用发现对不上
- 成本几乎为零：**复用了本来就要写的正则**，一份代码两个用途
  （同一个 `_PAGE_NUMBER_PATTERNS`：既清理页脚，又提取页码做审计）

**实测输出**（那份养老合同）

```
页脚页码非单调：1 处回退 / 共 50 页，例如 [(49, 1)]
1 页未提取到文本（第 [1] 页）—— 可能是整页图片（扫描的签字页 / 封面）
```

**两条都对得上事实**：第 1 页确实是封面，第 49 页确实有回退。

**判据**：**凡是"下游无条件信任"的字段，解析阶段就该给它一个自检。**

**来源**：Day 3 `app/core/parser.py`

**面试怎么用**：属于"数据质量怎么保证"。
"静默错位比报错更危险，所以解析层要做自检"是完整答案。

## D-016｜写入用 `upsert` 而非 `insert`

**决策**：`upsert_chunks` 调 `client.upsert`。

**为什么**

`chunk_id` 是**确定性**的（D-001）：同一份文档 + 同样的切分 → 同样的 id。
配合 `upsert`，重复导入命中同一批主键并**覆盖**，不产生副本。

**反过来会怎样（实测）**

| | `upsert` | `insert` |
| --- | --- | --- |
| 可查询行数 | 10 → **10** | 10 → **20** |
| 检索结果 | 正常 | **同一段原文出现两次**，挤占 top-k |

**两件事必须同时成立才有效**

1. **`chunk_id` 确定性**（D-001）—— 否则第二次是新主键，`upsert` 也救不了
2. **写入用 `upsert`**（本条）—— 否则命中了主键仍然新增

**代价**（详见 D-020）：`upsert` 在 Milvus 内部是「墓碑 + 插入」，
`get_collection_stats().row_count` 会虚高（10 → 20 → 30）。
**这不是 bug**，墓碑等 compaction 才清；但**断言不能用这个值**。

**来源**：Day 4 `app/core/vector_store.py`

**面试怎么用**：问"文档重复上传怎么处理"时，
"确定性 ID + upsert"是标准答案；补一句"upsert 内部是墓碑 + 插入"更好。

## D-017｜`index_type` 和 `metric_type` 是两个不同的东西

**决策**

```python
index_params.add_index(
    field_name="sparse",
    index_type="SPARSE_INVERTED_INDEX",   # 用什么数据结构存
    metric_type="BM25",                   # 怎么算相似度
)
```

**为什么**

两个参数回答的是不同的问题：

| 参数 | 回答 | 取值来源 |
| --- | --- | --- |
| `index_type` | **用什么数据结构存** | 向量 / 稀疏矩阵的索引结构 |
| `metric_type` | **怎么算相似度** | 距离或评分函数 |

`BM25` 只是一个**评分函数**，不是一种索引结构。
稀疏向量的倒排索引类型名是 `SPARSE_INVERTED_INDEX`。

**反过来会怎样**

- 把 `BM25` 填进 `index_type` → **`create_collection` 直接失败**，后面几步全跑不了
- 稀疏索引的 `metric_type` 若不是 `BM25` → **Function 白建**：
  稀疏向量里存的是 **BM25 词权重**，只有 BM25 打分器知道怎么解读
  （它需要文档频率、平均文档长度这些统计量）

**一个额外发现**：索引类型名是**原样透传给服务端的字符串**。
实测：在 pymilvus 源码里搜 `SPARSE_INVERTED_INDEX` / `HNSW` / `IVF_FLAT` —— **全部无匹配**。
意味着本地没有校验、没有自动补全，**拼错了要连上 Milvus 才报错**。

**来源**：Day 4 `app/core/vector_store.py::_build_index_params`（连填错两次后修正）

**面试怎么用**：问"稀疏检索用什么索引"或"Milvus 索引配置有哪些参数"时，
能讲清 `index_type` 与 `metric_type` 的分工就是满分答案。

## D-018｜`or` 做 None 合并对整数是错的

**决策**

```python
"page": chunk.page if chunk.page is not None else _NO_PAGE   # ✅
"page": chunk.page or _NO_PAGE                                # ❌
```

**为什么**

`or` 判断的是**真假值**，不是**是否为 None**。
而 `0` 在 Python 里是假值 —— 所以 `0 or -1` 会得到 `-1`。

**反过来会怎样**

- 实测 `page` 取值 `[2, 3, 5, 7, 8, 9, 10, 12]` —— **从 1 开始**
  （`parser.py` 用 `enumerate(pages, start=1)`），所以当前**踩不到**
- **但 `char_start` 可以是 0**（前言块的 `char_start=0`）。
  若对它用 `or`，位置信息会直接错掉
- 所以这个写法是「**碰巧正确**」，不是「正确」

**来源**：Day 4 `_chunk_to_row`。
当时三处**字符串**字段被改了，唯独唯一有风险的 **`page`** 漏了 ——
因为改动是照着"字符串那几行"做的，不是照着"`or` 对整数不安全"这个问题类别做的。

**面试怎么用**：不直接考。但"怎么识别一个碰巧能跑的写法"是代码质量讨论里的加分点。

## D-020｜Milvus 的 upsert = 墓碑 + 插入，所以 `row_count` 会虚高

**决策**

- 断言幂等性用 `query(filter="", output_fields=["count(*)"])`
- **不用** `get_collection_stats().row_count`

**为什么**

Milvus 的存储是**只追加**的：segment 一旦落盘就**不可变**，所以**没有原地更新**。

```
upsert 的真实动作 = 写一条删除标记（墓碑）+ 写入新行
```

- **查询**会过滤墓碑 → `count(*)` 得到真实值
- **`get_collection_stats`** 不过滤墓碑 → 统计值虚高
- 墓碑要等 **compaction**（后台段合并）才被物理清除

**反过来会怎样**

Day 4 实测：同一份文档写 3 次

| | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 统计值 | 10 | 20 | **30** |
| 真实可查询 | 10 | 10 | **10** |

**用统计值做断言 → 一个完全正确的 upsert 被判为失败。**
Day 4 实际发生了：验收报 ❌，害得去怀疑自己的实现。

**来源**：Day 4 `scripts/milvus_smoke.py` 第 3 步 + `vector_store.count_rows()`

**面试怎么用**：问"Milvus 的删除 / 更新是怎么实现的"——
标准答案就是**只追加 + 墓碑 + 查询时过滤 + compaction 回收**。

## D-022｜RRF 的分数尺度和单路完全不同

**决策**：混合检索用 `RRFRanker(k=60)`，**不**把两路分数加权求和。

**为什么**

```
RRF: score(d) = Σ 1 / (k + rank_i(d))
```

它**只用排名，不用原始分数** —— 所以对量纲不敏感。

**反过来会怎样**

Day 4 实测的分数范围：

| 路径 | 分数范围 |
| --- | --- |
| `dense` | 0.29 ~ 0.54 |
| `bm25` | 0.59 ~ **7.58** |
| `hybrid` | 0.032 ~ 0.033 |

- **直接相加** → BM25 那一路单方面说了算（7.58 对 0.54），
  向量检索的结果等于被淹没了
- RRF 的量级：`#1 名 = 1/(60+1) ≈ 0.0164`，**两路都排第一 ≈ 0.0328**
  （实测 hybrid top1 = 0.0328 正是这个含义）

**来源**：Day 4 `milvus_smoke.py` 实测输出

**面试怎么用**：问"混合检索怎么融合两路结果"时，这是完整答案。
能报出实测的分数范围，比只说"用 RRF"强得多。

## D-024｜重试只包单次 HTTP 调用，不包流式消费

**决策**：`_create_with_retry()` 只包 `chat.completions.create()` 这一句。
`stream()` 里消费流的 `async for` **故意留在重试范围之外**。

**为什么**

流已经 `yield` 给调用方的内容**收不回来**。重试整个生成器 =
用户看到前半段文字重复输出两遍。

正确的边界是：**重试只覆盖"还没吐出任何内容"的阶段。**

```
create() 失败        -> 还没吐字，安全重试          ✅
开始 yield 之后失败   -> 已经吐了，重试 = 重复输出   ❌ 直接抛错
```

因为重试恰好只包 `create()`，这个边界**自动成立**，不需要额外判断。

**重试策略的两个判断**

| 异常 | 重试 | 理由 |
| --- | --- | --- |
| `APIConnectionError` / `APITimeoutError` | ✅ | 瞬时网络问题 |
| `RateLimitError`（429） | ✅ | 加退避等待 |
| `APIStatusError` 且 `status_code >= 500` | ✅ | 服务端瞬时故障 |
| 401 / 400 | ❌ | **确定性失败** —— 重试不会改变错误的输入 |

> ⚠️ 5xx 要用 `status_code >= 500` 判断，**不要枚举**。
> 枚举很容易漏 —— 第一版漏掉了 **502**，而 502 恰恰是网关/代理层最常见的瞬时错误。

**反过来会怎样**

- 包住整个生成器 → 重试时前半段文字重复输出
- 枚举 5xx 而漏掉 502 → 网关抖动时请求直接失败，明明重试就能过
- 重试 401/400 → 浪费配额与时间，且把"输入有错"这个信息延迟暴露

**附带实现细节**：tenacity 的 `with attempt:` 对**不可重试的异常也先抑制**，
真正的判定发生在下一轮 `iter()`。所以计数器放在 `with` 之后也能数到每一次尝试
（实测：3 次尝试 → 计数 2 次重试；401 首次失败 → 计数 0 次重试）。

**来源**：Day 5 TODO-4（`app/core/llm.py`）

**面试怎么用**：问"流式接口怎么加重试"—— 标准答案就是这个边界划分。

## D-025｜材料标识与定位信息必须分开

**决策**：材料排版成

```
[a3f7d2b5a00c4596] 来源：第七章 研学旅游协议条款 · 第二十六条 · 合同生效 页码：25
第二十六条 合同生效
本合同一式 份，……
```

**标识独立成一个方括号，定位信息放在括号外。**

**为什么**

这两样东西的服务对象不同：

| | 标识 | 定位 |
| --- | --- | --- |
| 给谁用 | **机器 / 校验器** | **人 / 模型** |
| 要求 | 全局唯一、短、**模型必须精确复现** | 可读、帮模型说清"依据在哪" |
| 要不要模型抄 | **要** | **不要** |

**混在同一个括号里会出两个问题**：

1. 模型引用时得把章节、条款、标题、页码**全抄一遍** —— 抄错一个字就核对不上
2. 校验器**抓不到** —— 实测第一版写成 `[来源: id 章节 条款 标题 页码]`，
   校验器报「材料里出现的标识: **0 个**」，因为它期望方括号里只有一个 ID

**标识为什么用 `chunk_id` 而不是 `clause_no`**

`clause_no` **会重复** —— 附件里也有"第一条"，
实测那份养老合同里"第一条"出现了**两次**。只有 `chunk_id` 是全局唯一的。

**反过来会怎样**

- 标识和定位混一起 → 引用极易抄错，且校验器失效
- 用 `clause_no` 当标识 → 引用指向不唯一，核对等于没做

**来源**：Day 5 TODO-2（`app/core/rag.py::_format_context`）

**面试怎么用**：问"RAG 的引用怎么做才能核对"时，
"标识与定位分离"是那个能显出设计功力的点。

## D-026｜低温管随机性，不管编造

**决策**：`temperature=0.1` **之外**，提示词里仍然显式写
「只能依据材料回答，材料中没有相关内容就说'材料中无相关内容，无法回答'」。

**为什么**

| `temperature` 管什么 | 不管什么 |
| --- | --- |
| **采样随机性** —— 让模型在候选里更倾向高分项 | **编造** |

**幻觉不是随机性问题，是指令遵循问题。** 温度调到 0，
模型照样会自信地编一个"材料里没有、但听起来合理"的答案。

所以这两件事**必须分开做**：

- 低温 → 减少同一个问题两次回答不一致
- 约束 → 防止模型说材料里没有的事

**反过来会怎样**

- 以为低温就够 → 问一个材料里没写的问题（比如"违约金是多少"），
  会得到一个**编造的数字**，而且看起来很可信
- 这正是法务场景最危险的失败模式：**错误 + 自信**

**来源**：Day 5 TODO-3（`app/core/rag.py::SYSTEM_PROMPT`）

**面试怎么用**：问"审查类任务的 temperature 怎么设"时，
只答"设低温求确定性"是及格；
**补上"但低温不防幻觉，防幻觉靠约束"才是满分**。

## D-027｜引用核对必须同时查"编造"和"没引用"

**决策**：验收脚本同时核对**条款号**和**材料标识**，
并把「回答里一个标识都没有」判为**失败**。

**为什么**

一个只核对"编造的引用"的检查，会有**假阳性**：

```python
cited = set(re.findall(r"第[一二三四五六七八九十百零〇\d]+条", answer))
unknown = cited - hit_clauses
return 1 if unknown else 0          # ← 空集减空集 = 空集 -> 返回 0，通过
```

**如果模型一个引用都不写**：`cited` 是空集 → `unknown` 也是空集 →
**判定通过**。一个完全不引用、全靠编的回答会被判为合格。

**这个失败模式比漏检更危险**：漏检至少还显示"没查到"，
假阳性会给你一个 ✅，让你以为链路是好的。

**反过来会怎样**

- 只查编造 → 模型无视引用要求时，校验器报 ✅
- 只查条款号、不查标识 → 模型编一个假标识（`[deadbeef12345678]`）也发现不了

**设计上的一步**：标识的正则定义放在 `rag.py`，
**和生成它的 `_format_context` 放在一起**。分开定义的话，
将来改了格式而忘了改校验器，校验器**不会报错**，
只会安静地告诉你"没有引用" —— 又是一次静默失效。

**来源**：Day 5 校验器加强（`scripts/rag_demo.py`）

**面试怎么用**：属于"**怎么保证你的评估本身可信**"这一类问题。
能讲出"检查本身也会有假阳性"，是评测意识的体现。

## D-028｜`to_thread` 买的是并发响应性，不是单请求速度

**决策**：`chunk_document` / `parse_document` 一律 `await asyncio.to_thread(...)`，
与 `model_runtime` / `vector_store` 保持一致。

**为什么**

同步阻塞调用跑在 `async def` 里，会**冻住整个事件循环** ——
期间所有请求都不能被处理，并发能力归零。

实测（`scripts/blocking_probe.py`，50 页 PDF，解析约 1.5s）：

| | 轻任务调度延迟 | 重任务自身耗时 |
| --- | --- | --- |
| 直接在事件循环里 | **1519.1 ms** | 1519.2 ms |
| `asyncio.to_thread` | **0.1 ms** | 1477.4 ms |

**轻任务被拖慢约 13000 倍；而重任务自己几乎没变（差 3%）。**

**反过来会怎样**

- **用单请求测这个改动，一定得出"没有区别"** —— 因为改的本来就不是它的耗时。
  这是最容易被误判为"改动无效"的地方。
- 不丢线程池 → 一次上传会让所有人的提问卡住 1.5 秒以上

**边界（容易答漏的一半）**

| | `to_thread` 的效果 |
| --- | --- |
| 并发**响应性** | ✅ 大幅改善 |
| **吞吐量**（CPU 密集部分） | ❌ 不变 —— GIL 让线程的 CPU 工作仍然串行 |

**推论**：想要真正的 CPU 并行要用**进程**（多 worker），不是线程。
`to_thread` 只保住响应性，没给算力。

**判据**：多慢才值得丢线程池？`to_thread` 自己有几微秒开销。
实测 `parse_document` ≈ 1500ms（必须丢）；`chunk_document` ≈ 几毫秒（丢不丢都行，为一致性丢了）。

**来源**：Day 6 TODO-1（`app/core/ingest.py`、`app/api/v1/documents.py`）

**面试怎么用**：问"FastAPI 里怎么处理 CPU 密集任务"时，
能讲出"线程保响应性、进程要吞吐"这一组区分，而不是笼统说"用线程池"。

## D-029｜"检索为空"不等于"没有可用依据"

**决策**：`grounded` 由**回答是否引用了材料**决定，而不是由**检索是否返回结果**决定。

```python
grounded = bool(citations) and "无法回答" not in result.answer
```

**为什么**

第一版写的是 `if not result.hits: grounded = False`。**这几乎是死代码** ——
稠密检索**永远返回 top-k**，`result.hits` 只有在集合为空时才会是空的。

真正的信号在**回答**里：模型有没有给出可核对的结论。

**这个 bug 只有跑起来才看得见**

验收脚本对一个知识库里没有的问题发问，返回：

```
200  {"answer":"结论：材料中无相关内容，无法回答。\n\n依据：\n- 第二十四条 ... [936...]"}
```

**模型拒绝了，却照样给出了一条"依据"** —— 因为提示词的输出格式
强制它永远填一段「依据」。于是：

- `citations` 非空
- `grounded` 保持 `True`
- "无依据率"这个指标**永远不会触发**

单看 `query.py` 没问题，单看 `SYSTEM_PROMPT` 也没问题，**合起来就错了**。

**反过来会怎样**

- 用"检索为空"判断 → 该分支基本不执行，"答不上来"完全隐形
- 只改代码不提示词 → 模型继续在拒绝时硬填依据，`grounded` 仍不可信
- 所以修复必须**两边一起动**：提示词加「材料不足时只输出一行『无法回答』，不要写依据段」，
  代码才有一个可靠信号可读

**来源**：Day 6（`app/core/rag.py::SYSTEM_PROMPT` + `app/api/v1/query.py`）

**面试怎么用**：属于"**跨层契约**"类问题 ——
一个字段的语义，取决于上下游是否按同一个假设工作。

## D-030｜对外契约与内部模型必须分开

**决策**：`app/api/v1/schemas.py` 独立于 `app/core/schemas.py`。
`Citation` 不复用 `SearchHit`。

**为什么**

两者生命周期不同：

| | 内部模型（`SearchHit`） | 对外契约（`Citation`） |
| --- | --- | --- |
| 谁在用 | 检索、编排、评测 | 前端、第三方、SDK |
| 改动影响 | 内部重构 | **破坏调用方** |
| 字段 | 11 个（含 score / char_start / char_end） | 4 个（用户真正需要的） |

**照搬内部模型会怎样**：对外契约被内部实现绑死 ——
以后改检索层（比如 `section` 拆成 `chapter` + `section`）就得升接口版本。

**三个具体决定**

1. **`chunk_id` 必须暴露**（约定 5）—— 不给 ID，前端就没法把引用定位回条目
2. **字段名用对外名**（`clause_location` / `original_text`），不用内部名 ——
   内部改名时接口不用动
3. **`original_text` 给全文，不截断** —— 用途是"核对"，截断就核不了。
   真要限体积应该**限条数**（只给回答实际引用的那几条），不要限单条长度

**反过来会怎样**

- 直接 `return SearchHit` → 契约泄露内部字段，且内部一改就破坏调用方
- 截断 `original_text` → 用户无法判断原话有没有被曲解，"可核对"变成空话

**来源**：Day 6 TODO-2（`app/api/v1/schemas.py`）

**面试怎么用**：问"API 响应模型怎么设计"时，
"内外分离 + 只暴露用户需要的字段"是标准答案的核心。

## D-031｜冷启动开销必须在 lifespan 付掉

**决策**：`main.py` 的 lifespan 里预热**三样**：
本地模型、Milvus 连接、tiktoken 词表。

**为什么**

每一样都只在**第一次**付，但付的时候恰好是**第一个真实请求**：

| 冷启动项 | 实测 | 不预热的后果 |
| --- | --- | --- |
| Milvus 首次建连 | **4.1 s** | 第一个上传请求多等 4 秒 |
| tiktoken 词表加载 | **2.4 s** | 第一个提问请求多等 2.4 秒 |
| 本地模型加载 | 1.3 s | （Day 2 已经预热了） |

**怎么发现的 tiktoken 那一笔**

分段耗时对不上账：

```
total_ms  5871.1
segments  retrieve 213.5 + llm 3223.6 = 3437.1
未计入    2434 ms          ← 没有任何 span 覆盖
```

嫌疑落在 `count_messages_tokens()` 上（它内部 `tiktoken.get_encoding`）。
挪进 lifespan 后重测：

```
total_ms  2934.7 ；segments 合计 2933.4 ；未计入 1.3 ms
```

**2434 ms → 1.3 ms，假设被证实。**

**反过来会怎样**

- 不预热 → 每个 worker 的第一个请求都慢几秒，且**用户会以为是服务本身慢**
- 不打点 → 这笔开销**完全隐形**，"总耗时 5871 但各段加起来 3437"这种账
  不主动对账就永远看不见

**两条分界线**

| 项 | 放哪 | 为什么 |
| --- | --- | --- |
| Milvus 连接 | **fail-fast 的 try 里** | 它是核心依赖，连不上就不该对外提供服务 |
| tiktoken | **try 外面** | 加载失败不致命，`count_tokens` 会退化为按字符估算，不该因此拒绝启动 |

**来源**：Day 6（`app/main.py` lifespan）

**面试怎么用**：问"服务刚启动时第一个请求为什么慢"——
能报出具体毫秒数并说明"已挪进预热"，比说"有冷启动问题"强得多。

## D-032｜开发默认端口不用 8000

**决策**：前端默认连 `http://127.0.0.1:8010`（可用 `CONTRACTLENS_API` 覆盖），不用 8000。

**为什么**

8000 是开发机上**最容易撞**的端口 —— 各种 demo、agent、本地代理都默认用它。
而 Windows 有个陷阱：

> **允许不同进程分别监听 `0.0.0.0:8000` 和 `127.0.0.1:8000`。**

于是 `netstat` 显示端口 `LISTENING`，**但请求被另一个服务抢走**。
排查成本极高：后端日志一切正常，前端报"连不上"，中间没有任何报错。

**反过来会怎样（Day 7 实际发生）**

前端报"后端未就绪"，实际打 `/health` 返回的是：

```json
401 {"error": "Authentication required"}
```

**这根本不是我们的服务在应答** —— 我们的 `/health` 返回带 `status` / `app` / `models_ready`，
FastAPI 的错误格式也是 `{"detail": ...}`，绝不会是 `{"error": ...}`。

如果只看 netstat 的 LISTENING 就断定"后端起来了"，会一直往 uvicorn 配置上找方向，
永远找不到 —— 因为**问题不在后端**。

**一条可复用的判断方法**

> **「端口在监听」≠「你的服务在监听」。**
>
> 验证服务真的起来，不能靠 `netstat`，要**打一个已知内容的请求**，
> 检查返回体里有没有【你自己的字段】。返回体的形状是比端口状态可靠得多的证据。

**代价**：改一个默认端口，成本几分钟；不改，可能耗掉半天。

**来源**：Day 7 前后端联调

**面试怎么用**：属于"**怎么确认一个假设成立**"这一类问题。
"端口在监听"和"服务在跑"是两个假设 —— 能讲清怎么用返回体证伪前者，是排障思维的体现。

## D-033｜RAG 与 Agent 不是替代关系，是双层分工

**决策**：简单问题走 RAG 快路径（一次检索 + 一次生成）；
**置信度不足时才升级到 Agent**（多步、换工具、跨文档）。

**为什么**

用同一批问题在两种形态下实测对比：

| 问题 | RAG | Agent |
| --- | --- | --- |
| 合同什么时候生效 | 答得出，引用正确 | 同样正确，但**多花 2~4 次 LLM 调用** |
| **第十五条 的原文是什么** | **搜 4 次拿不到，只能说"无法确认"** | **2 步，一次 `get_clause_details` 给出全文** |
| 三份合同各自的生效条款 | **做不到**（一次检索只返回混合 top-k） | `list_documents` → 逐份精确取 |
| 第一百零五条存在吗 | "没检索到"（信息量低） | 逐份枚举后说"三份都没有" |

**后三行是能力差异，不是体验优化** —— 这才是 Agent 的正当性。

**两种形态的本质差异**

| | RAG | Agent |
| --- | --- | --- |
| 延迟 | ✅ 可预测（检索 70~140ms + LLM 2~3s） | ❌ 2~4 步，**2~3 倍**且步数有随机性 |
| 成本 | ✅ token 固定 | ❌ 步数 × token |
| 可测性 | ✅ 给定材料 → 输出可断言 | ❌ 同问题两次跑法不同（EXP-008） |
| 失败模式 | ✅ 少 | ❌ 多（死循环、选错工具、strand 调用） |
| 检索策略 | ❌ 永远 top-k，**不会换措辞、不会换工具** | ✅ 实测第一搜失败、第二搜成功 |
| 多跳 / 跨文档 | ❌ 做不到 | ✅ 能做到 |

**反过来会怎样**

- **全用 Agent** → 简单问题也背 2~3 倍延迟和成本，且行为不可测
- **全用 RAG** → 「第十五条原文」那类问题永远答不出，只能退回"无法确认"

**切换信号（已有基础设施）**

`grounded=false` / 引用对不上 / 检索分数明显偏低 → 升级到 Agent。

**来源**：A 周末架构自审（对比数据见 EXP-008 / EXP-010 / EXP-011）

**面试怎么用**：问"你为什么用 Agent"时，**答"因为更先进"是减分**。
正确答法是：「我先做了 RAG，实测它在'精确取某条款'和'跨文档对比'上做不到，
所以加了 Agent 层，但简单问题仍然走 RAG 快路径。」—— 这是**架构判断**，不是技术追新。

## D-034｜工具的价值在于覆盖 RAG 做不到的场景，不在数量

**决策**：加工具前先问一句 —— **「这件事，单次 RAG 能做到吗？」**
做不到才值得加。

**为什么**

玩具 Agent 的工具（`get_weather` / `calculator`）演示价值为零 ——
因为它们和 Agent 的核心能力无关。

用这把尺子量现有三个工具：

| 工具 | 类型 | 过标准吗 |
| --- | --- | --- |
| `search_clauses` | 只读检索 | ⚠️ 这就是 RAG 本身 |
| `get_clause_details` | 只读精确 | ✅ **过了** —— 解决了"相似度检索拿不到特定条款"这个根本局限 |
| `list_documents` | 只读元信息 | ✅ 勉强过 —— 支撑了"跨文档"这个 RAG 做不到的场景 |

**反过来会怎样**

追求工具数量 → 加一堆**同质的只读工具**，能力没变，只是 prompt 变长、选择变难。

**当前真正的短板不是数量，是「动作多样性」**

三个工具**全是"读"**，没有"算"、没有"写"、没有"外部"。
场景覆盖太窄：现在只能回答"某个条款讲了什么"。

**B 周该补的（按价值）**

| 工具 | 为什么值 | RAG 能做到吗 |
| --- | --- | --- |
| **`compare_clauses(doc_a, doc_b, keyword)`** | 跨文档对比（"哪份对甲方更不利"） | ❌ **完全做不到** |
| `extract_obligations(doc_id)` | 抽取义务清单（需结构化输出） | ⚠️ 勉强，质量差 |

**建议 B3 加 `compare_clauses`** —— 它是**"这是 Agent 不是 RAG"最有力的证据**，
因为 RAG 架构下**根本无法表达**这个操作。

**面试怎么用**：面试官不会数工具个数。他们看的是：
你为什么加这个工具、怎么写的 description、怎么判断连调是否浪费。
**这三样比"5 个工具"值钱。**

---

**记录纪律**：每条都要写「反过来会怎样」。
写不出来，说明还停在"知道怎么做"，没到"知道为什么不能那么做"。
