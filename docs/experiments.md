## EXP-001｜query 指令前缀对检索的影响

**状态**：🔄 待 W2 用排序指标复测

### 问题

`bge-base-zh-v1.5` 官方推荐在检索时给 query 加指令前缀
（`为这个句子生成表示以用于检索相关文章：`），doc 侧不加。

本项目要不要加？加了是正收益还是负收益？

### 方法（Day 2 首测 —— 方法有缺陷，见「为什么结论不成立」）

- **样本**：1 对文本
  - query = `合同什么时候生效`
  - doc = `本合同自双方签字之日起生效`
- **指标**：两者的余弦相似度
- **对照组**：`EMBEDDING_QUERY_INSTRUCTION` 设为指令前缀 vs 设为空字符串
- **脚本**：`scripts/smoke_test_models.py` 第 4 步

### 结果

| 项 | 值 |
| --- | --- |
| 不加前缀 cos(query, doc) | `0.7466` |
| 加前缀 cos(query, doc) | `0.5701` |
| 差值 | `-0.1765`（负值） |

> **Day 3 修订**：差值 `-0.1765` 是最初设定的噪声阈值（0.02）的 **近 9 倍**，
> **不能再用「噪声」解释**。下面的结论已据此修订。

### 这个数字说明什么、不说明什么

#### ✅ 它说明：前缀对 query 编码有**大幅、真实**的影响

0.1765 的绝对余弦落差不是随机波动。前缀有 18 个 token，
而 query 本身只有十几个字 —— 加前缀相当于**在查询里塞进比正文还多的通用文本**，
query 向量必然被推离原位。这符合预期，也排除了「测不出来」的可能。

#### ❌ 它不说明：检索变差了

**关键缺陷：只有一个 doc，没有干扰项。**

前缀可能让 query 到**所有** doc 的余弦都下降（整体位移）。
若所有 doc 等幅下降，**排序完全不变，检索结果一模一样**。

用单对文本**无法区分**这两种情况：

| 情况 | 对检索的影响 | 本次测量能否识别 |
| --- | --- | --- |
| query 只远离了这一个 doc | 有害 | ❌ 不能 |
| query 远离了所有 doc（等幅） | **无影响** | ❌ 不能 |

所以 0.18 的正确解读是：**「前缀的影响很大」**，而**不是**「前缀有害」。

#### 另外两点仍然成立

- **n = 1**：单点无法推广到其他 query
- **场景不匹配**：该前缀是为 **s2p（短查询 → 长段落）** 设计的；
  本项目是**短 query → 短条款**

#### ⚠️ 更有价值的一点：注释里有乱码

填入值时 `EMBEDDING_QUERY_INSTRUCTION` 曾在 `.env` 里出现过**中文乱码**风险
（`.env` 若存成 GBK，前缀会变成一串 `?` 且不报错）。
本次测量本身不受影响（脚本读的是 `settings` 默认值），
但**这提醒了一条纪律：含中文的配置项必须确保文件是 UTF-8**。

### 结论（Day 3 修订）

**默认改为关闭前缀**，理由：

1. 存在一个**大幅、可复现**的负向效应，虽然指标不完美，但**方向明确**；
2. 模型卡的推荐针对 **s2p（长段落）**，与本项目的**短条款**场景不符；
3. **迁移成本为零**（见下），现在关掉，W2 若被数据推翻就改回来 —— 两边都不亏；
4. 不带证据开启一个变换，比不带证据关闭它更危险 —— **开启会产生实际影响，关闭不会**。

> 修订说明：Day 2 我给的结论是「保持开启」，依据是「证据不足时不动」。
> 数字填进来之后证据强度变了（0.18 ≫ 0.02），所以默认值也应该跟着变。
> **这是一次基于数据的修订，不是摇摆。**

### 关键事实：这个决策的迁移成本为零

**前缀只加在 query 侧，doc 侧永不加。**

> 也就是说，开不开前缀，**Milvus 里存的向量完全相同**。

这跟"换 embedding 模型"有本质区别——后者要改维度、重建集合、全量重灌。
前缀是纯查询时的行为，**任何时候改一行配置就纠正，不需要重灌任何数据**。

**所以它不值得在 Day 3 纠结。**

### 后续（W2）

**不需要为它单独搭框架。** 检索链路（Day 3–4）跑通后，这自然是一项可做的对比：

```
10 组 query（每组一个已知正确条款 + 若干干扰条款）
  ├─ 不加前缀 → 编码 → Top-5 检索
  └─ 加前缀   → 编码 → Top-5 检索
比较 recall@1 / recall@5 / MRR
```

**指标必须是排序指标，样本量至少 10 组**，否则重复 Day 2 的错误。

这正好并入 **W2 §14.1 检索方案对比**，不用单独排期。W4 的 60 条评测集是正式版。

**决策点**：若 W2 的 recall@5 差异 < 2 个百分点 → 直接保持默认（不加前缀，少一次字符串拼接）。
若差异显著 → 按数据定，并写进 README 的结果表。

### 面试价值

这个实验的价值**不在结论，在于暴露了一个"看起来是 A/B，其实测不出 B"的陷阱**：

> "我做过一次 query 指令前缀的对比，一开始用单对余弦，发现是负收益。
> 后来意识到指标不对——前缀优化的是排序而不是绝对相似度，
> 而且我那是短文本对，不是它设计的 s2p 场景。
> 改成正例/干扰项的 recall 比较之后，结论才可靠。"

**能说清"我第一次测量错在哪"，比直接说"测出来前缀没用"有说服力得多。**

## EXP-002｜本地模型冷启动与推理延迟基线

**状态**：✅ 完成（数字来自 `logs/app.log`）

### 问题

本地 CPU 推理的延迟是多少？后续 W2 延迟优化、W4「本地 vs API」对比实验，
需要一个**起点数字**。

### 方法

- 模型：`BAAI/bge-base-zh-v1.5`（embedding，768 维）、`BAAI/bge-reranker-base`（rerank）
- 环境：Windows / Python 3.12 / CPU，`TORCH_NUM_THREADS=4`
- 来源：`warmup_embedder()` / `warmup_reranker()` 的日志计时，
  计的是**加载模型 + 一次假推理**的完整耗时

### 结果

| 场景 | embedding | rerank |
| --- | --- | --- |
| **进程首次**（OS 页缓存冷） | 0.90 s | 1.78 s |
| **后续进程**（OS 页缓存热） | 0.24 – 0.28 s | 1.03 – 1.11 s |

原始日志：

```
15:39:57  embedding 就绪，冷启动 0.90s     ← 首次
15:39:59  rerank    就绪，冷启动 1.78s
15:42:46  embedding 就绪，冷启动 0.28s     ← 之后三次
15:42:47  rerank    就绪，冷启动 1.11s
15:44:34  embedding 就绪，冷启动 0.24s
15:44:35  rerank    就绪，冷启动 1.03s
15:46:23  embedding 就绪，冷启动 0.25s
15:46:24  rerank    就绪，冷启动 1.09s
```

### 结论

1. **冷启动比预期快得多。** 原计划文档里写的是"10–30 秒"，实测 1–2 秒。
   原因是模型文件已进 OS 页缓存，且模型本身不大（102M / 278M 参数）。

2. **rerank 是瓶颈**，约为 embedding 的 **4 倍**（1.1 s vs 0.25 s），
   尽管预热输入只有一条短文本。原因见下。

3. **⚠️ 这两个数字都是"页缓存热"的。** Docker 容器冷启动时页缓存是空的，
   数字会显著变大。**W6 做容器化时必须重测**，不要把这里的数字写进 README 的结果表。

### 原理：为什么 rerank 慢 4 倍

| | Embedding（Bi-Encoder） | Rerank（Cross-Encoder） |
| --- | --- | --- |
| 前向次数 | 1 次 / 文本 | **1 次 / (query, doc) 对** |
| 能否预计算 | ✅ 文档向量可离线算好入库 | ❌ 必须在线算 |
| 模型规模 | 102 M | 278 M |

**rerank 的耗时随候选数线性增长，而 embedding 不随查询增长**——
这正是"精排是本地部署瓶颈"的根本原因，也是 W2 要优化的方向：

- 候选池 Top-20 → **Top-10**（直接砍一半）
- 截断长度 `max_length` 512 → **256**
- 精排结果缓存

- W2 Day 13：检索方案对比实验
- W4 Day 28：本地 vs API 对比实验（本表是"本地"那一侧的分母）

## EXP-003｜真实合同 PDF 的解析与切分

**状态**：⚠️ 测出 4 个真实缺陷（P0–P3），待修

### 问题

`parser.py` + `chunker.py` 在合成 fixture（`tests/fixtures/test_contract.md`）上全部测试通过。
**这套逻辑在真实合同 PDF 上成立吗？**

合成文档永远测不出的三件事：真实排版（页眉页脚 / 表格 / 跨页）、文档结构不规范、
以及**内容重复**。

### 方法

- **样本**：`data/samples/clean/` 下 2 份官方示范文本 PDF
  - **A**：`关于推行《黑龙江省养老机构服务合同（试行）（示范文本）》的通知.pdf`

  - **B**：`附件6研学旅游合同（示范文本）.pdf` —— 13230 字，带完整章节结构
- **策略**：`clause`，`CHUNK_MAX_CHARS=400`，模型上限 512 token
- **脚本**：`scripts/inspect_chunks.py` + 两个临时诊断脚本

#### 🔴 P0｜`chunk_id` 碰撞（已实际发生）

```
chunks = 78    unique_ids = 76    dup_groups = 2
→ 以 chunk_id 作主键时，2 个块会被静默覆盖

id = bf8b0d019dc0deed   x2
    clause='第一条'  char_start=  259  page=2   len=264
    clause='第一条'  char_start=23130  page=51  len=264
id = 1f05ae56e77cec6f   x2
    clause='第二条'  char_start=  524  page=2   len=72
    clause='第二条'  char_start=23395  page=51  len=72
```

**根因**：`_make_chunk_id` 的输入是 `doc_id|clause_no|index/total|text` —— **不含位置**。
同一份文档里出现相同条款文本，且都属于「同名条款的第 1/1 块」时，ID 必然相同。

**为什么会发生**：这份 PDF 的物理第 2 页装的是文档第 49 页的内容（见下「附带发现」），
等于**末页在开头重复了一遍**。

**后果**：`chunk_id` 作 Milvus 主键时，后写入的块覆盖先写入的块。
文本虽然相同，但 `page` / `char_start` 不同 —— **引用会指向错误的位置**。
编码约定 5（引用可回溯）被破坏。

**为什么合成 fixture 测不出**：fixture 里没有任何重复文本，`test_chunk_ids_are_unique` 全绿。

**修法**：把位置纳入 ID。

```python
raw = f"{doc_id}|{char_start}|{clause_no or ''}|{index}/{total}|{text}"
```

#### 🔴 P1｜最后一个条款吞掉文档尾部

| 条款 | 块数 | 占比 |
| --- | --- | --- |
| **第十五条**（A） | **33 / 78** | **42%** |
| **第二十六条**（B） | 7 / 51 | 14% |

**根因**：条款标题只在正文出现。**附件、签字页、评估表格里没有「第X条」**，
这些行全部被追加到「当前条款」名下。

**后果（比 P0 更严重）**：`clause_no` 不再可信。报告里引用「第十五条」去说明一个
其实来自**附件表格**的问题 —— **ID 有效但语义错误**，这比没有 ID 更危险，
因为它**看起来是对的**。

这直接违反了约定 5 的初衷，而且**静默发生**。

**修法方向**（Day 4/5 处理）：

- 引入「分节哨兵」：`附件N`、`以下无正文`、签字页特征 → flush 当前条款，
  后续行归入无条款号的独立块
- 或给单条款设累积上限，超限后的续写块**丢弃 `clause_no`**
- **核心原则：宁可没有条款号，也不要错误的条款号**

#### 🟠 P2｜页眉页脚剔除完全没生效

A 文档中 `第 N 页 共 49 页` 全部保留在块文本里
（见 `[01] [07] [08] [25] [45] [60] [66] [70]` …）。

**根因**：`_strip_headers_footers` 按**精确字符串**统计跨页重复。
而页码每页不同（「第 3 页」vs「第 4 页」），每个字符串计数恒为 1，
**永远达不到 60% 阈值**。

**教训**：**「跨页重复」启发式只对固定文本有效，对带变量的页眉页脚
（页码、日期、生成时间）无效。**

**修法**：必须加模式规则，不能只靠字符串相等。

```python
_FOOTER_PATTERNS = (
    re.compile(r"^第\s*\d+\s*页\s*共\s*\d+\s*页$"),
    re.compile(r"^\d+\s*/\s*\d+$"),
    re.compile(r"^Page\s+\d+\s+of\s+\d+$", re.IGNORECASE),
)
```

#### 🟡 P5｜`inspect_chunks.py` 在 stdout 被重定向时崩溃

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u23ce'
```

脚本里用了 `↳`（U+21B3）和 `⏎`（U+23CE）。
**Windows 下 Python 对真实控制台走 Unicode 通道（所以手动运行没事），
一旦 stdout 被管道重定向就退化为 GBK（cp936）** → 崩溃。

**这个 bug 只在重定向 / CI 时出现**，正是最不容易被发现的地方。

**修法**（脚本开头两行）：

```python
if hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

### 附带发现：页码单调性是一个极低成本的自检

物理页序 vs 页脚标注（A 文档，51 物理页 / 文档自身 49 页）：

```
extract# 1  -> (无文本)
extract# 2  -> 49/49     ← 错位：文档末页出现在物理第 2 页
extract# 3  ->  1/49
extract# 4  ->  2/49
...
extract# 51 -> 49/49

序列: [49, 1, 2, 3, ..., 48, 49]      monotonic 48/49
```

**这个检查一眼就发现了人工翻 78 个块绝对看不出来的问题**，
而且它复用的正是 P2 要写的那个页码正则 —— **一份代码，两个用途**。

**建议加进 `parse_pdf`**：

| 检查 | 触发条件 | 价值 |
| --- | --- | --- |
| 页码非单调 | 序列出现回退 | 提示「物理页序与文档页码不符，文本顺序可能错位」 |
| 页面无文本 | 有页数但该页 0 字符 | 提示「可能是整页图片（如扫描的签字页）」 |

### ✅ P1 修复（Day 4）：分节哨兵

**根因**：条款边界只认「第X条」，而附件、签署页、评估表格里**没有条款号**，
于是全部被追加到最后一个条款名下。

**方案**：引入**分节哨兵**，命中即结束当前条款，后续内容成为**无条款号**的独立组。

| 哨兵 | 正则要点 | 例 |
| --- | --- | --- |
| 附件标题 | `^附件\s*(\d+\|一\|A)` + 边界断言 | `附件1 技术服务清单` |
| 正文结束 | 整行只有「以下无正文」 | `以下无正文`（纯标记，**直接丢弃**） |
| 签署区 | 整行**以**「（盖章/签名/签字）」**结尾**的短行 | `甲方（盖章）：` `乙方监护人（签名或盖章）：` |

签署区的规则故意用「以括号结尾」而不是角色词（甲方/乙方）——
这样能覆盖「乙方监护人（签名或盖章）：」这类变体；
而正文里括号后面还有字、不会以括号为行尾，天然被排除。

**两个反直觉的设计决定：**

1. **没有用「条款长度上限」兜底。** 真正超长的**条款**应该被切成多块但
   **都保留 `clause_no`** —— 那是 `_split_long_clause` 的职责。
   长度上限无法区分「长条款」和「条款 + 尾部垃圾」，
   用它会在解决一个错误的同时制造另一个。
2. **签署区不逐行开新组。** 只有当前是**有条款号**的正文时才断开；
   若已在尾部组里就继续追加 —— 否则「甲方（盖章）」「乙方（签名）」「日期」
   会各自变成 5 个字的噪声 chunk。

**同时修掉一个潜在 bug**：原实现在「章节标题 flush 之后、下一条款之前」的普通行
因为没有 current 而**倒回往 preamble 里塞**，这会把文档中段的内容插到文档最开头、
位置信息全乱。新实现用 `started` 标志区分「文档开头」和「正文中段」。

`tests/test_chunker.py` → **18 passed**（新增 4 条 P1 回归用例）。

## EXP-004｜条款号查询被交叉引用压制

**状态**：🔄 现象与根因已确认 → W2 §14.1 验证改进方案

### 问题

用**纯条款号**查询（如「第十二条」）时，BM25 能不能准确命中那个条款？

法务场景里这是最典型的查询之一：用户想知道「第十二条讲了什么」。

### 方法

- **数据**：`附件6研学旅游合同（示范文本）.pdf`（52 块，已入库）
- **查询**：`第十二条`
- **观察**：BM25 的 top-3，以及每个命中块的文本长度

### 结果

Day 4 实测：

| 排名 | BM25 分 | 条款 | 含「第十二条」次数 | 块长 |
| --- | --- | --- | --- | --- |
| **1** | 16.315 | **第十五条** | 1 | **167** |
| 2 | 14.490 | 第二十四条 | 1 | 272 |
| **3** | 11.840 | **第十二条** ✅ | 1 | **362** |

**三个块的命中次数完全相同，而分数与块长严格成反比。**

同一次查询的三条路径对比：

| 路径 | top1 | 结果 |
| --- | --- | --- |
| dense | 第十二条 · 旅游者解除合同 | ✅ |
| **bm25** | **第十五条 · 旅行社协助旅游者返程** | ❌ |
| **hybrid** | **第十二条 · 旅游者解除合同** | ✅ |

### 根因

**BM25 的长度归一化**（公式里的 `b` 参数）：

```
score = IDF × tf×(k1+1) / (tf + k1×(1 - b + b × dl/avgdl))
                                                    ↑ 文档越长 -> 分母越大 -> 分越低
```

第十五条里出现「第十二条」**不是因为它讲的是第十二条，而是因为交叉引用**
（合同里「按照本合同第十二条的约定…」这类句子到处都是）。

结论：**一个短条款只要"提到"某个条款号，就能在关键词检索里压过那个条款本身。**

这对本项目特别重要 —— **合同里交叉引用是常态**，
而「某个条款讲了什么」正是核心查询类型。

### 结论

**现象与根因已确认；改进方案待验证。**

假说：**当 query 是纯条款号形态（`^第.+条$`）时，应优先匹配 `clause_no` 字段而非正文。**
用户此时问的是「这个条款本身讲什么」，不是「哪里提到了它」。

候选做法（W2 评估）：

- 用标量过滤把 `clause_no` 相等的结果提到最前
- 或在 query 里识别出条款号后直接走标量过滤，绕开 BM25 排序

> ⚠️ **不要凭这一个查询下结论。** n = 1。
> 但与 EXP-001 不同的是：**这次的根因是确定的**（长度归一化 + 交叉引用），
> 所以它可以带着明确假说进 W2，而不是"测不出来"。

### 附带观察：RRF 修正了单路的错误

同一次查询里，hybrid 的 top1 是正确的（0.0323 —— 两路都排第一的量级）。
**BM25 错了、dense 对了，融合后对了。**

这算混合检索的一个正面证据 —— 但**同样只是 n = 1**，
正是 W2 §14.1 要系统验证的东西。

## EXP-005｜tiktoken 对中文的 token 估算偏差

**状态**：✅ 已测出（有确定倍数）→ W2 决定是否校正

### 问题

`llm.py` 用 `tiktoken` 的 `cl100k_base` 估算 token 数，
用于**上下文预算检查**与成本量级判断。

但 DeepSeek 用的不是这套词表。**估算值到底偏多少？**

### 方法

- 数据：Day 5 的 10 条检索材料（约 2000 字中文）
- 对比：`llm_client.count_messages_tokens(messages)` 的估算值
  vs API 返回的 `usage.prompt_tokens` 真实值

### 结果

Day 5 实测（模型 `deepseek-flash` @ `api.deepseek.com`）：

| | tokens |
| --- | --- |
| 估算（tiktoken `cl100k_base`） | **2037** |
| 真实（`usage.prompt_tokens`） | **1261** |
| **偏差** | **1.62 倍** |

### 原因

`cl100k_base` 对中文的切分比 DeepSeek 的真实 tokenizer **碎得多** ——
同一段中文，前者切出的 token 数明显更多。

### 影响

上下文预算是**按估算值**卡的：

```
RAG_CONTEXT_MAX_TOKENS = 3000
  按估算算  ->  占 68%
  按实际算  ->  占 42%
```

**预算会提前 26 个百分点触发截断** —— 明明还有一大半窗口没用上，
代码却以为快满了。

偏差方向是**安全**的（高估 = 保守），不会撑爆上下文。
但如果**按估算值去调 `RAG_TOP_K`**，会得出错误结论 ——
"只能放 5 条"实际上可能是"能放 12 条"。

### 结论

**已测出确定倍数 1.62x。** 是否校正留给 W2，三个选项：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| A. 不校正 | 保守着用 | 浪费约一半上下文窗口 |
| B. 硬编码系数 | 估算值 ÷ 1.6 | 换模型就要重测 |
| C. 用真实 usage 反向校准 | 每次调用后用实际值修正系数 | 需要持久化状态 |

> ⚠️ 这个倍数**只对「中文 + `deepseek-flash`」成立**。
> 换模型（尤其换以英文为主、词表不同的模型）必须重测。
> 唯一可移植的做法是 C。

| --- | --- |
| 决定是否校正、采用哪个方案 | W2 |
| 换 LLM / embedding 模型后重测 | W4 |

## EXP-006｜`to_thread` 对并发响应性与单请求耗时的影响

**状态**：✅ 完成

### 问题

把阻塞调用挪进 `asyncio.to_thread` 之后，**用单请求去测，耗时几乎不变**。

那它到底改善了什么？还是说这个改法本来就没有效果？

### 方法

脚本：`scripts/blocking_probe.py`

同时调度两件事：

- **heavy()** —— `parse_document` 解析一份真实 PDF（50 页，2641 KB），CPU 密集
- **light()** —— 什么也不做，只记录"我什么时候被调度到"

`light` 开始得越晚，说明事件循环被 `heavy` 卡得越久。

### 结果

Day 6 实测（三次取平均，各预热两轮）：

| | 轻任务调度延迟 | 重任务自身耗时 |
| --- | --- | --- |
| ❌ 直接在事件循环里 | **1519.1 ms** | 1519.2 ms |
| ✅ `asyncio.to_thread` | **0.1 ms** | 1477.4 ms |

- **轻任务被拖慢约 13000 倍**
- **重任务自身几乎没变（差 3%）**

### 结论

`to_thread` 买的是**并发响应性**，不是**单请求速度**。

| | 效果 |
| --- | --- |
| 并发**响应性** | ✅ 大幅改善（1519ms → 0.1ms） |
| **吞吐量**（CPU 密集部分） | ❌ 不变 —— GIL 让线程的 CPU 工作仍然串行 |

**推论**：想要真正的 CPU 并行要用**进程**（多 worker），不是线程。

**判据**：`to_thread` 自身有约几十微秒开销，所以太快的函数丢进去反而更慢。
实测 `parse_document` ≈ 1500 ms（必须丢）、`chunk_document` ≈ 几毫秒（丢不丢都行）。

> ⚠️ **最容易踩的坑**：用单请求验证这个改动，必然得出"没有区别"，
> 从而误判为"改动无效"甚至回滚它。**必须用并发场景测。**

### 后续

| 项 | 何时 |
| --- | --- |

| 评估是否需要多 worker（进程级并行） | W4 |

## EXP-007｜服务冷启动开销拆解

**状态**：✅ 完成

### 问题

服务启动后的**第一个**上传请求要 5784 ms，而同样一份 1 KB 的 Markdown、
第二次只要（相对）更短。**慢在哪？**

### 方法

两路夹击：

1. **看日志时间戳的空档** —— 找出哪一步之间有大段空白
2. **对账分段耗时** —— `total_ms` 减去各 `segments` 之和，
   差额就是"没有被任何 span 覆盖"的隐藏开销

### 结果

**逐项拆解**：

| 冷启动项 | 实测 | 隐藏在哪 |
| --- | --- | --- |
| 本地模型加载（embedding + rerank） | 1.3 s | lifespan（Day 2 已预热） |
| **Milvus 首次建连** | **4.1 s** | `vector_store._get_client()`，懒加载，第一个上传请求触发 |
| **tiktoken 词表加载** | **2.4 s** | `count_messages_tokens()` 内部，**不打点完全看不见** |

**对账证据（tiktoken 那一笔怎么被发现的）**：

```
预热前：total_ms 5871.1 ；segments 合计 3437.1 ；未计入 2434 ms
预热后：total_ms 2934.7 ；segments 合计 2933.4 ；未计入 1.3 ms
```

**2434 ms → 1.3 ms**，假设被证实。

**顺带收益**：`search_dense` 从 72 ms 降到 6 ms（第二次请求），因为 Milvus 连接已预热。

### 结论

**每一项冷启动都只在第一次付，而付的时候恰好是第一个真实请求** ——
用户会以为是"服务本身慢"。

**必须主动对账**：如果只记总耗时、不做"总减各段"的差额检查，
tiktoken 那 2.4 秒**永远不会被发现**。

| 项 | 放哪 | 为什么 |

| Milvus 连接 | **fail-fast 的 try 里** | 核心依赖，连不上就不该对外提供服务 |
| tiktoken 词表 | **try 外面** | 加载失败不致命，`count_tokens` 会退化为按字符估算 |

## EXP-008｜Agent 循环的收敛速度不稳定

**状态**：✅ 已测出（同一问题跑两次，一次耗尽一次收敛）

### 现象

同一个问题跑两次 —— 一次最大 6 步耗尽，一次 5 步收敛。

### 分段诊断

- ✅ **好的**：第 1 步检索有噪声，在后面步骤更换查询语句，重新检索追到目标条款。
- ❌ **问题**：第 1 次超最大步数还未收敛，导致耗尽，第 2 次 5 步就收敛。

### 根因

循环缺信息充分判断和预算感知。

### 修法一：新增信息量检测

记录每次查询出来的新增 `chunk_id`，每次对比是否有新增：
没有则插入提示「无新增信息，应该可以作答」，有则继续。

### 修法二：预算感知

每次计算剩余步数，注入系统提示词。

### 验证：A3 前后对照

| | A3 前 | A3 后 |
| --- | --- | --- |
| 步数序列 | 6（**耗尽**）、5 | **3, 4, 3, 4, 3** |
| 均值 | 5.5 | **3.4** |
| 区间 | [5, 6] | **[3, 4]** |
| 预算耗尽率 | **50%** | **0%** |

**两条机制的直接证据**：

- **信息充分判断**：2 次独立触发 —— 检索返回的条目全部已在集合中 → 注入提示 → 模型立刻收尾
- **预算感知**：注入值 `[5, 4, 3, 2]`，**单调递减**（恒定的数字不构成感知）

**结论**：增加这两个机制后，步数明显稳定在 3~4 步内得到准确回答。

### 附带发现：检索工具返回的信息量，限制了 Agent 的能力

**现象**：大模型找到了目标条款，但不确定它在哪个文档中，**反问用户是哪个文档**。

**量化**：修好 A3 之后的 5 次运行，**5 次全部反问** —— 说明不是模型随机，是结构性缺陷。

**根因**：检索工具只返回 `[chunk_id] 章节 · 条款 · 页码 · 原文`，**没有文档标识**。
模型知道条款内容，但不知道它归属哪份合同。

**改法**：在检索工具的返回里增加 `doc_id`（改动只有几行）。

**验证**：增加之后，大模型可以直接指出条款来自哪个文档，不再反问。

**结论**：**工具的返回信息也影响着 Agent 的能力。**
不给模型判断所需的字段，它再聪明也只能反问用户。

> **方法论提醒**：单次反问可能只是随机，**5/5 都反问才说明是结构性问题**。
> 判断"是不是系统缺陷"要看多次运行的分布，不是看单次表现。

## EXP-009｜Agent 的失败模式实测：工具异常与工具预算耗尽

**状态**：✅ 已测出（两个场景各一次真实记录）

### 为什么做这个实验

`call_tool` 里写了一条设计：**工具出错不抛异常，而是把错误当成一条观察结果返回。**
理由是"错误也是输入的一部分"——但这条设计**从没被验证过**。

同时 `for...else` + `budget_exhausted` 的退化路径也从没跑过。

> **"写了"不等于"在工作"。** 这个项目里已经因此踩过三次坑。

---

### 场景一：工具抛异常

**做法**：让 `_list_documents` 直接 `raise RuntimeError("故意炸一下")`。

**结果**：

```
[工具返回] 错误：list_documents 执行失败（RuntimeError: 故意炸一下）。可以换个方式再试。
```

Agent **没有崩**，继续用同一轮里成功的那次检索作答。而最关键的是它在最终答案里**主动认账并下调了结论强度**：

> "我尝试列出知识库文档清单以确认入库了几份合同，但该工具调用失败（RuntimeError），
> 因此我**无法给出文档总数和完整清单**，上面的'多份'判断**仅来自检索结果中出现的不同文本特征**。"

**结论**：错误作为观察的设计成立。而且模型表现出**区分"能推断的"与"无法确认的"** 的能力 ——
比崩溃或假装没事都好。

---

### 场景二：工具预算为 0

**做法**：`--max-steps 1`，于是第一轮注入的剩余步数就是 `0`。

**结果**：

```
步数 1 · 步数变化 [0] · 工具调用 0 次
```

模型**拒绝编造**，并解释了为什么：

> "我目前无法查证这个问题 —— 我的工具调用次数已经用完了（剩余 0 次）……
> 按照规则，合同生效时间这类结论必须引用合同原文，不能凭印象或常识猜
> （比如「签字盖章之日起生效」只是行业惯例，不代表你这份合同就这么写）。"

**结论**：「不编造」约束在**零工具的极端压力下**依然生效。这是一条很强的证据 ——
它不是靠"检索结果好看"撑住的，是靠约束本身。

---

### 附带发现：判定信号又一次不足以区分情况

验收脚本当时这样判：

```python
if s["tool_calls"] == 0:
    print("❌ ... 那是 RAG，不是 Agent")
```

但 `tool_calls == 0` 有**两个完全不同的原因**：

| 原因 | 判定 |
| --- | --- |
| (a) 有预算却不调工具、凭记忆作答 | ❌ 真失败 |
| (b) 预算为 0，被禁止调工具 | ✅ **正确的退化** |

**这是本项目第四次同类误判**：

| 次数 | 位置 | 表现 |
| --- | --- | --- |
| 1 | `rag_demo` 的引用核对 | 空集减空集 = 通过；模型完全不引用也能"合格" |
| 2 | `grounded` | 由"检索为空"决定，而稠密检索永远返回 top-k → 几乎永远 True |
| 3 | `agent_demo` 的 `bool(answer)` | 兜底文案「我没能在 N 步内完成」也算"有答案" |
| 4 | **`tool_calls == 0`** | 正确退化（预算为 0）被判成 RAG 退化 |

**修法**：先看 `budget_trace` 最小值是否为 0，再决定怎么判。

**规律**：**只要一个字段承载两种含义，判定就必然出错。**
要么给字段分层，要么给判定加前置条件。

## EXP-010｜工具选择行为与错误参数处理

**状态**：✅ 已测出

### 背景

A2 之前，Agent 问「第十五条 合同生效及附件」时反复搜 4 次，返回的一直是第二十六条，
最后只能说"我无法确认"。补了一个**精确取全文**的工具 `get_clause_details`。

### 一、加一个工具，差距为什么这么大

> **原因：原本的工具都是相关性近似搜索，可能带回噪音；
> 新加的是精确匹配 —— 有就是有，没有就是没有。**

补充一层：近似检索返回的是「top-k 最相似」，
这和「这条条款到底在不在库里」**没有必然关系** —— 哪怕把 k 加大，也可能永远拿不到某一条。
精确匹配一次就能确定"有没有"，所以不必再靠反复换措辞去逼近。

**实测对比**：

| | A2 前 | A2 后 |
| --- | --- | --- |
| 步数 | 4（反复换措辞搜索） | **2** |
| 工具调用 | 4 次 `search_clauses` | **1 次 `get_clause_details`** |
| 结果 | "我无法确认" | **完整原文 + 文档 + 页码** |

### 二、三种问题下的工具选择（实测）

| 问题 | 步数 | 调用的工具 | 结果 |
| --- | --- | --- | --- |
| A「第十五条 合同生效及附件 的原文是什么」 | **2** | `get_clause_details` | 直接给出全文 |
| B「合同什么时候生效」 | 4 | `search_clauses` → `list_documents` → `search_clauses` → `get_clause_details` | 给出两份文档各自生效条款 |
| C「第一百零五条 的原文是什么」 | 4 | `list_documents` → `get_clause_details` ×4 → `search_clauses` | 逐文档枚举后如实说查不到 |

**规律**：

- **已知条款号** → 走精确取全文，步数最少
- **只有问题描述** → `search_clauses` + `list_documents` 是必调的，`get_clause_details` 概率性出现
- 两次运行「原文类」问题，都是只调精确工具 —— **说明 description 写对了**

### 三、连调怎么判：合理还是浪费

> **判据一：每次调用的参数是否相同。相同 → 原地浪费。**

**补上判据二**（这是 EXP-008 那种情况）：

> **参数不同时，看返回内容是否新增。**
> 换措辞搜了 3 次、返回的 `chunk_id` 全是旧的 —— 同样是浪费，只不过更隐蔽。

**所以完整判据是两层**：

| 情况 | 判定 |
| --- | --- |
| 参数相同 | 一定浪费（同一工具、确定性，结果必然一样） |
| 参数不同，但返回条目全是旧的 | **浪费**（零新增信息） |
| 参数不同，且拿到了新条目 | **合理**（在逐步逼近） |

**C 那次连调 4 次 `get_clause_details` 属于哪一种？** —— 合理：
每次换一个 `doc_id`，是在**排除"某份文档漏查"**的可能，属于有意义的降级策略。

### 四、错误参数的处理（四个单元测）

直接调 `call_tool`，**不要靠"等模型给错"来测**：
前者测的是"工具对错误参数是否健壮"，后者是在等运气。

| # | 输入 | Python 层面发生什么 | 日志级别 |
| --- | --- | --- | --- |
| ① | `{}` | 缺必填参数 → `TypeError`，**在调用边界被挡** | warning |
| ② | `{"wrong": 1}` | 多余关键字 → `TypeError`，**在调用边界被挡** | warning |
| ③ | `{"clause_no": 123}` | **签名检查通过**，在 `_escape_expr` 深处 `123.replace()` → `AttributeError` | **exception** |
| ④ | `no_such_tool` | `_HANDLERS.get()` 返回 None，走前置判断 | warning |

**③ 是唯一一个"通过边界、在深处炸"的** —— 所以它落到了 `except Exception` 分支。

**为什么这暴露了问题**：

> **输入错误不该打成 exception。**
> 保留 exception 的话，第一眼会以为是**系统异常**，去排查；
> 但系统其实正常，只是**模型生成的参数有误**。

**改法**：全部降为 `warning`，并在消息里带上参数内容。

**代价要写下来**：工具自身的真 bug 也会被降级成 warning，
所以**必须带全上下文（工具名 + args）才分得清**。

### 五、这个实验的面试价值

> **最值钱的不是工具本身，是「连调」那套判据。**
> 因为它**不是亲身跑过就很难看到** —— 光看代码你不会知道模型会连调 4 次、
> 也不会知道那 4 次到底是浪费还是在排除可能性。

**面试时的用法**：面试官问「你怎么知道 Agent 该不该再查一次」，
答「我有两层判据：参数相同 / 返回零新增」—— 这个回答只有真跑过的人才给得出。

### 后续

| 项 | 何时 |
| --- | --- |
| 把"参数相同"这层判据也做进循环（目前只做了"零新增"） | 可选，看 A4 后是否还出现浪费 |
| 工具 schema 的三个坑（`parameter`/`str`/示例格式）→ 记进 decisions | A4 前 |

## EXP-011｜手写 ReAct vs LangGraph：数据与踩坑记录

**状态**：🔄 数据已齐，**结论待填**（见文末四个问题）

### 目的

不是"用框架再实现一遍"，而是回答两个面试必问的问题：

1. **LangGraph 帮我做了什么？**
2. **它没帮我做什么？**

### 方法

同一批问题、两个实现（`app/agent/react.py` 手写版 / `app/agent/graph.py` 图版本），
对比「步数」与「budget_trace」。

### 数据一：单次对比

| 问题 | 图版本 | 手写版本 | 是否一致 |
| --- | --- | --- | --- |
| 合同什么时候生效 | 4 步 `[5,4,3,2]` | 4 步 `[5,4,3,2]` | ✅ 完全一致 |
| 第十五条 合同生效及附件 的原文是什么 | 2 步 `[5,4]` | 2 步 `[5,4]` | ✅ 完全一致 |
| 第一百零五条 的原文是什么 | **3 步** `[5,4,3]` | **4 步** `[5,4,3,2]` | ❌ 差 1 步 |

**差异细节（第三题）**：

- 图版本：`get_clause_details` → `list_documents` + `search_clauses` → 收尾（只搜 1 次）
- 手写版：`list_documents` + `get_clause_details` + `search_clauses` ×3 → 收尾（搜了 3 次）
- **手写版的答案更详尽**（逐份文档列出了"条款号最高不超过第二十四条"），图版本只说"没查到"

### 数据二：各跑 3 次

| 实现 | 观察 |
| --- | --- |
| 图版本 | 步数与工具调用**每次一致** |
| 手写版本 | 步数与工具调用**有波动** |

> ⚠️ **n = 3，且两个实现的 `SYSTEM_PROMPT` 是两份独立文件、消息结构也不同 —— 不能直接归因。**

### 数据三：硬上限验证

做法：临时删掉 SYSTEM_PROMPT 里的预算提示，并设 `MAX_STEPS = 2`（让模型不知道预算，才会一直想调工具）。

| 项 | 结果 |
| --- | --- |
| steps / budget_trace | `2` / `[1, 0]` |
| 判定 | ❌ 步数用尽（2/2）仍未得出结论 |
| **轨迹异常** | 第 2 步发出了 `search_clauses`，但**没有任何 `[工具返回]`** |

**说明**：条件边在 `tools_node` **之前**就切断了，于是历史里留下一条
「有 `tool_calls`、但没有对应 `tool` 消息」的 assistant 记录。

### 数据四：A4 期间踩到的 bug（共 8 个）

| # | bug | 类别 |
| --- | --- | --- |
| 1 | `json.load` 应为 `json.loads` | 函数用错 |
| 2 | `"assitant"` 应为 `"assistant"` | 键名/拼写 |
| 3 | `"id"` 应为 `"tool_call_id"` | 键名 |
| 4 | `return "tool"` 应为 `"tools"` | 路由键名 |
| 5 | `"search_clause"` 应为 `"search_clauses"` | 键名 |
| 6 | `"steps": remaining` 应为 `state["steps"] + 1` | 语义搞反 |
| 7 | `answer` 字段从未赋值（影子状态） | 状态设计 |
| 8 | `user` 提示插在 `tool` 消息之间 → 400 | 协议约束 |

### 结论

**一、框架改变了什么**

「2 个一致、1 个差 1 步」是**观察到**的结果，还不足以说成结论 ——
要说成结论，至少各自跑 50 次做分布对比。

但可以从实现上确定的差异是：

> **框架把「隐式的状态变量手动修改」变成了「显式的自动修改 + 部分手动」，
> 并且把「思考」和「执行」解耦了。**

- 手写版：一整轮 `for` 里既调模型又执行工具，思考和执行混在一起
- 图版本：`agent` 和 `tools` 是**两个节点**，中间隔着一条边 —— **解耦是结构性的，不是靠代码规范**

**二、为什么不能说"图更稳"**

影响因素太多：`temperature=0.1` 的采样随机、两个实现的 `SYSTEM_PROMPT` 是两份独立文件、
预算提示注入位置不同、消息结构不同。

**要归因，先看手写版自己稳不稳** —— 同一实现跑多次。
如果它自己在波动，那和框架无关，是实现细节（prompt / 消息结构）导致的。

**三、硬上限截断的隐患**

单次运行不受影响（这条不完整记录不会再被使用）。

**但续跑会** —— 从「有 `tool_calls` 却没有对应 `tool` 消息」的记录恢复时，
API 会报 400（同 EXP-009 场景一那类协议错误）。

**所以 A5 接 checkpointer 之前，必须先处理这条记录**（补齐 `tool` 消息 / 丢弃该条 / 
把上限判断移到工具执行之后）。

**四、8 个 bug 该由谁负责（这一条第一次答错了）**

| 类别 | bug | 谁的责任 | 说明 |
| --- | --- | --- | --- |
| 键名 / 拼写 | `assitant`、`id`、`tool`、`search_clause` | **自己** | 框架完全不校验 |
| **语义 / 设计** | `steps` 语义反了、`answer` 影子状态 | **自己**（不是框架） | 框架只负责"值怎么传"，**不知道这个值是什么意思** |
| **协议** | `json.loads`、tool 消息必须连续 | **自己**（API 只是事后拒绝） | 报错在调用时，根因在组装时 |

**第一版答成「语义/设计类归框架管」是错的。** 框架无法知道你把 `steps` 赋成了 `remaining` ——
它没有你的意图。

> 唯一间接的帮助是：State 用 `Annotated` 强制你回答"这个字段该追加还是覆盖"，
> 让 `answer` 这种影子状态**更容易被发现**，但它不会替你发现。

**所以"用框架买到了什么"的最终答案**：

| 买到了 | 没买到 |
| --- | --- |
| **结构**：状态声明化、循环图化、条件边可组合 | **正确性**：键名、语义、协议全不管 |
| **可扩展性**：checkpoint、可视化、人工中断 | **意图**：它不知道你想干嘛 |
| **解耦**：思考与执行变成两个节点 | **免费的边界**：步数上限要自己加 |
