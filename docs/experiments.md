## EXP-001｜query 指令前缀对检索的影响

**状态**：🔄 待 W2 用排序指标复测

### 问题

`bge-base-zh-v1.5` 官方推荐在检索时给 query 加指令前缀
（`为这个句子生成表示以用于检索相关文章：`），doc 侧不加。

本项目要不要加？加了是正收益还是负收益？

### 方法（Day 2 首测 —— 方法有缺陷，见「为什么结论不成立」）

- **样本**：1 对文本
  - query = `合同什么时候生效`
  - doc = `本合同自双方签字之日起生效`
- **指标**：两者的余弦相似度
- **对照组**：`EMBEDDING_QUERY_INSTRUCTION` 设为指令前缀 vs 设为空字符串
- **脚本**：`scripts/smoke_test_models.py` 第 4 步

### 结果

| 项 | 值 |
| --- | --- |
| 不加前缀 cos(query, doc) | `0.7466` |
| 加前缀 cos(query, doc) | `0.5701` |
| 差值 | `-0.1765`（负值） |

> **Day 3 修订**：差值 `-0.1765` 是最初设定的噪声阈值（0.02）的 **近 9 倍**，
> **不能再用「噪声」解释**。下面的结论已据此修订。

### 这个数字说明什么、不说明什么

#### ✅ 它说明：前缀对 query 编码有**大幅、真实**的影响

0.1765 的绝对余弦落差不是随机波动。前缀有 18 个 token，
而 query 本身只有十几个字 —— 加前缀相当于**在查询里塞进比正文还多的通用文本**，
query 向量必然被推离原位。这符合预期，也排除了「测不出来」的可能。

#### ❌ 它不说明：检索变差了

**关键缺陷：只有一个 doc，没有干扰项。**

前缀可能让 query 到**所有** doc 的余弦都下降（整体位移）。
若所有 doc 等幅下降，**排序完全不变，检索结果一模一样**。

用单对文本**无法区分**这两种情况：

| 情况 | 对检索的影响 | 本次测量能否识别 |
| --- | --- | --- |
| query 只远离了这一个 doc | 有害 | ❌ 不能 |
| query 远离了所有 doc（等幅） | **无影响** | ❌ 不能 |

所以 0.18 的正确解读是：**「前缀的影响很大」**，而**不是**「前缀有害」。

#### 另外两点仍然成立

- **n = 1**：单点无法推广到其他 query
- **场景不匹配**：该前缀是为 **s2p（短查询 → 长段落）** 设计的；
  本项目是**短 query → 短条款**

#### ⚠️ 更有价值的一点：注释里有乱码

填入值时 `EMBEDDING_QUERY_INSTRUCTION` 曾在 `.env` 里出现过**中文乱码**风险
（`.env` 若存成 GBK，前缀会变成一串 `?` 且不报错）。
本次测量本身不受影响（脚本读的是 `settings` 默认值），
但**这提醒了一条纪律：含中文的配置项必须确保文件是 UTF-8**。

### 结论（Day 3 修订）

**默认改为关闭前缀**，理由：

1. 存在一个**大幅、可复现**的负向效应，虽然指标不完美，但**方向明确**；
2. 模型卡的推荐针对 **s2p（长段落）**，与本项目的**短条款**场景不符；
3. **迁移成本为零**（见下），现在关掉，W2 若被数据推翻就改回来 —— 两边都不亏；
4. 不带证据开启一个变换，比不带证据关闭它更危险 —— **开启会产生实际影响，关闭不会**。

> 修订说明：Day 2 我给的结论是「保持开启」，依据是「证据不足时不动」。
> 数字填进来之后证据强度变了（0.18 ≫ 0.02），所以默认值也应该跟着变。
> **这是一次基于数据的修订，不是摇摆。**

### 关键事实：这个决策的迁移成本为零

**前缀只加在 query 侧，doc 侧永不加。**

> 也就是说，开不开前缀，**Milvus 里存的向量完全相同**。

这跟"换 embedding 模型"有本质区别——后者要改维度、重建集合、全量重灌。
前缀是纯查询时的行为，**任何时候改一行配置就纠正，不需要重灌任何数据**。

**所以它不值得在 Day 3 纠结。**

### 后续（W2）

**不需要为它单独搭框架。** 检索链路（Day 3–4）跑通后，这自然是一项可做的对比：

```
10 组 query（每组一个已知正确条款 + 若干干扰条款）
  ├─ 不加前缀 → 编码 → Top-5 检索
  └─ 加前缀   → 编码 → Top-5 检索
比较 recall@1 / recall@5 / MRR
```

**指标必须是排序指标，样本量至少 10 组**，否则重复 Day 2 的错误。

这正好并入 **W2 §14.1 检索方案对比**，不用单独排期。W4 的 60 条评测集是正式版。

**决策点**：若 W2 的 recall@5 差异 < 2 个百分点 → 直接保持默认（不加前缀，少一次字符串拼接）。
若差异显著 → 按数据定，并写进 README 的结果表。

### 面试价值

这个实验的价值**不在结论，在于暴露了一个"看起来是 A/B，其实测不出 B"的陷阱**：

> "我做过一次 query 指令前缀的对比，一开始用单对余弦，发现是负收益。
> 后来意识到指标不对——前缀优化的是排序而不是绝对相似度，
> 而且我那是短文本对，不是它设计的 s2p 场景。
> 改成正例/干扰项的 recall 比较之后，结论才可靠。"

**能说清"我第一次测量错在哪"，比直接说"测出来前缀没用"有说服力得多。**

## EXP-002｜本地模型冷启动与推理延迟基线

**状态**：✅ 完成（数字来自 `logs/app.log`）

### 问题

本地 CPU 推理的延迟是多少？后续 W2 延迟优化、W4「本地 vs API」对比实验，
需要一个**起点数字**。

### 方法

- 模型：`BAAI/bge-base-zh-v1.5`（embedding，768 维）、`BAAI/bge-reranker-base`（rerank）
- 环境：Windows / Python 3.12 / CPU，`TORCH_NUM_THREADS=4`
- 来源：`warmup_embedder()` / `warmup_reranker()` 的日志计时，
  计的是**加载模型 + 一次假推理**的完整耗时

### 结果

| 场景 | embedding | rerank |
| --- | --- | --- |
| **进程首次**（OS 页缓存冷） | 0.90 s | 1.78 s |
| **后续进程**（OS 页缓存热） | 0.24 – 0.28 s | 1.03 – 1.11 s |

原始日志：

```
15:39:57  embedding 就绪，冷启动 0.90s     ← 首次
15:39:59  rerank    就绪，冷启动 1.78s
15:42:46  embedding 就绪，冷启动 0.28s     ← 之后三次
15:42:47  rerank    就绪，冷启动 1.11s
15:44:34  embedding 就绪，冷启动 0.24s
15:44:35  rerank    就绪，冷启动 1.03s
15:46:23  embedding 就绪，冷启动 0.25s
15:46:24  rerank    就绪，冷启动 1.09s
```

### 结论

1. **冷启动比预期快得多。** 原计划文档里写的是"10–30 秒"，实测 1–2 秒。
   原因是模型文件已进 OS 页缓存，且模型本身不大（102M / 278M 参数）。

2. **rerank 是瓶颈**，约为 embedding 的 **4 倍**（1.1 s vs 0.25 s），
   尽管预热输入只有一条短文本。原因见下。

3. **⚠️ 这两个数字都是"页缓存热"的。** Docker 容器冷启动时页缓存是空的，
   数字会显著变大。**W6 做容器化时必须重测**，不要把这里的数字写进 README 的结果表。

### 原理：为什么 rerank 慢 4 倍

| | Embedding（Bi-Encoder） | Rerank（Cross-Encoder） |
| --- | --- | --- |
| 前向次数 | 1 次 / 文本 | **1 次 / (query, doc) 对** |
| 能否预计算 | ✅ 文档向量可离线算好入库 | ❌ 必须在线算 |
| 模型规模 | 102 M | 278 M |

**rerank 的耗时随候选数线性增长，而 embedding 不随查询增长**——
这正是"精排是本地部署瓶颈"的根本原因，也是 W2 要优化的方向：

- 候选池 Top-20 → **Top-10**（直接砍一半）
- 截断长度 `max_length` 512 → **256**
- 精排结果缓存

- W2 Day 10：加精排延迟优化 → 与本表对比，量化收益
- W2 Day 13：检索方案对比实验
- W4 Day 28：本地 vs API 对比实验（本表是"本地"那一侧的分母）

## EXP-003｜真实合同 PDF 的解析与切分

**状态**：⚠️ 测出 4 个真实缺陷（P0–P3），待修

### 问题

`parser.py` + `chunker.py` 在合成 fixture（`tests/fixtures/test_contract.md`）上全部测试通过。
**这套逻辑在真实合同 PDF 上成立吗？**

合成文档永远测不出的三件事：真实排版（页眉页脚 / 表格 / 跨页）、文档结构不规范、
以及**内容重复**。

### 方法

- **样本**：`data/samples/clean/` 下 2 份官方示范文本 PDF
  - **A**：`关于推行《黑龙江省养老机构服务合同（试行）（示范文本）》的通知.pdf`
    —— 51 物理页 / 23568 字，实为「通知 + 多份附件模板」合订本
  - **B**：`附件6研学旅游合同（示范文本）.pdf` —— 13230 字，带完整章节结构
- **策略**：`clause`，`CHUNK_MAX_CHARS=400`，模型上限 512 token
- **脚本**：`scripts/inspect_chunks.py` + 两个临时诊断脚本

### 结果

| 指标 | A（通知 + 附件） | B（研学旅游合同） |
| --- | --- | --- |
| 解析块 / 字符 | 1272 / 23568 | 729 / 13230 |
| 切分块数 | 78 | 51 |
| 平均长度 | 312 字 | 259 字 |
| 最长块 | 400 字 | 400 字 |
| **覆盖章节** | **0** | **7** |
| 超限块（> 512 tok） | 0 | 0 |
| **唯一 chunk_id** | **76 / 78（2 组碰撞）** | — |

**结论：合成 fixture 全绿，真实数据暴露 4 个缺陷。**

#### 🔴 P0｜`chunk_id` 碰撞（已实际发生）

```
chunks = 78    unique_ids = 76    dup_groups = 2
→ 以 chunk_id 作主键时，2 个块会被静默覆盖

id = bf8b0d019dc0deed   x2
    clause='第一条'  char_start=  259  page=2   len=264
    clause='第一条'  char_start=23130  page=51  len=264
id = 1f05ae56e77cec6f   x2
    clause='第二条'  char_start=  524  page=2   len=72
    clause='第二条'  char_start=23395  page=51  len=72
```

**根因**：`_make_chunk_id` 的输入是 `doc_id|clause_no|index/total|text` —— **不含位置**。
同一份文档里出现相同条款文本，且都属于「同名条款的第 1/1 块」时，ID 必然相同。

**为什么会发生**：这份 PDF 的物理第 2 页装的是文档第 49 页的内容（见下「附带发现」），
等于**末页在开头重复了一遍**。

**后果**：`chunk_id` 作 Milvus 主键时，后写入的块覆盖先写入的块。
文本虽然相同，但 `page` / `char_start` 不同 —— **引用会指向错误的位置**。
编码约定 5（引用可回溯）被破坏。

**为什么合成 fixture 测不出**：fixture 里没有任何重复文本，`test_chunk_ids_are_unique` 全绿。

**修法**：把位置纳入 ID。

```python
raw = f"{doc_id}|{char_start}|{clause_no or ''}|{index}/{total}|{text}"
```

---

#### 🔴 P1｜最后一个条款吞掉文档尾部

| 条款 | 块数 | 占比 |
| --- | --- | --- |
| **第十五条**（A） | **33 / 78** | **42%** |
| **第二十六条**（B） | 7 / 51 | 14% |

**根因**：条款标题只在正文出现。**附件、签字页、评估表格里没有「第X条」**，
这些行全部被追加到「当前条款」名下。

**后果（比 P0 更严重）**：`clause_no` 不再可信。报告里引用「第十五条」去说明一个
其实来自**附件表格**的问题 —— **ID 有效但语义错误**，这比没有 ID 更危险，
因为它**看起来是对的**。

这直接违反了约定 5 的初衷，而且**静默发生**。

**修法方向**（Day 4/5 处理）：

- 引入「分节哨兵」：`附件N`、`以下无正文`、签字页特征 → flush 当前条款，
  后续行归入无条款号的独立块
- 或给单条款设累积上限，超限后的续写块**丢弃 `clause_no`**
- **核心原则：宁可没有条款号，也不要错误的条款号**

#### 🟠 P2｜页眉页脚剔除完全没生效

A 文档中 `第 N 页 共 49 页` 全部保留在块文本里
（见 `[01] [07] [08] [25] [45] [60] [66] [70]` …）。

**根因**：`_strip_headers_footers` 按**精确字符串**统计跨页重复。
而页码每页不同（「第 3 页」vs「第 4 页」），每个字符串计数恒为 1，
**永远达不到 60% 阈值**。

**教训**：**「跨页重复」启发式只对固定文本有效，对带变量的页眉页脚
（页码、日期、生成时间）无效。**

**修法**：必须加模式规则，不能只靠字符串相等。

```python
_FOOTER_PATTERNS = (
    re.compile(r"^第\s*\d+\s*页\s*共\s*\d+\s*页$"),
    re.compile(r"^\d+\s*/\s*\d+$"),
    re.compile(r"^Page\s+\d+\s+of\s+\d+$", re.IGNORECASE),
)
```

#### 🟠 P3｜`section` 对无章节文档为空，且无法与识别失败区分

A 文档输出 `覆盖章节：0 个`。但**「文档本来就没有章」和「章节识别失败」

#### 🟡 P5｜`inspect_chunks.py` 在 stdout 被重定向时崩溃

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u23ce'
```

脚本里用了 `↳`（U+21B3）和 `⏎`（U+23CE）。
**Windows 下 Python 对真实控制台走 Unicode 通道（所以手动运行没事），
一旦 stdout 被管道重定向就退化为 GBK（cp936）** → 崩溃。

**这个 bug 只在重定向 / CI 时出现**，正是最不容易被发现的地方。

**修法**（脚本开头两行）：

```python
if hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

### 附带发现：页码单调性是一个极低成本的自检

物理页序 vs 页脚标注（A 文档，51 物理页 / 文档自身 49 页）：

```
extract# 1  -> (无文本)
extract# 2  -> 49/49     ← 错位：文档末页出现在物理第 2 页
extract# 3  ->  1/49
extract# 4  ->  2/49
...
extract# 51 -> 49/49

序列: [49, 1, 2, 3, ..., 48, 49]      monotonic 48/49
```

**这个检查一眼就发现了人工翻 78 个块绝对看不出来的问题**，
而且它复用的正是 P2 要写的那个页码正则 —— **一份代码，两个用途**。

**建议加进 `parse_pdf`**：

| 检查 | 触发条件 | 价值 |
| --- | --- | --- |
| 页码非单调 | 序列出现回退 | 提示「物理页序与文档页码不符，文本顺序可能错位」 |
| 页面无文本 | 有页数但该页 0 字符 | 提示「可能是整页图片（如扫描的签字页）」 |

### ✅ P1 修复（Day 4）：分节哨兵

**根因**：条款边界只认「第X条」，而附件、签署页、评估表格里**没有条款号**，
于是全部被追加到最后一个条款名下。

**方案**：引入**分节哨兵**，命中即结束当前条款，后续内容成为**无条款号**的独立组。

| 哨兵 | 正则要点 | 例 |
| --- | --- | --- |
| 附件标题 | `^附件\s*(\d+\|一\|A)` + 边界断言 | `附件1 技术服务清单` |
| 正文结束 | 整行只有「以下无正文」 | `以下无正文`（纯标记，**直接丢弃**） |
| 签署区 | 整行**以**「（盖章/签名/签字）」**结尾**的短行 | `甲方（盖章）：` `乙方监护人（签名或盖章）：` |

签署区的规则故意用「以括号结尾」而不是角色词（甲方/乙方）——
这样能覆盖「乙方监护人（签名或盖章）：」这类变体；
而正文里括号后面还有字、不会以括号为行尾，天然被排除。

**两个反直觉的设计决定：**

1. **没有用「条款长度上限」兜底。** 真正超长的**条款**应该被切成多块但
   **都保留 `clause_no`** —— 那是 `_split_long_clause` 的职责。
   长度上限无法区分「长条款」和「条款 + 尾部垃圾」，
   用它会在解决一个错误的同时制造另一个。
2. **签署区不逐行开新组。** 只有当前是**有条款号**的正文时才断开；
   若已在尾部组里就继续追加 —— 否则「甲方（盖章）」「乙方（签名）」「日期」
   会各自变成 5 个字的噪声 chunk。

**同时修掉一个潜在 bug**：原实现在「章节标题 flush 之后、下一条款之前」的普通行
因为没有 current 而**倒回往 preamble 里塞**，这会把文档中段的内容插到文档最开头、
位置信息全乱。新实现用 `started` 标志区分「文档开头」和「正文中段」。

### 验证（Day 4）

`tests/test_chunker.py` → **18 passed**（新增 4 条 P1 回归用例）。

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| **A 文档最大条款组** | **第十五条 33/78 = 42%** | **第四条 5/84 = 6%** |
| A 文档 第十五条 | 33 块 | **2 块** |
| A 文档 第三条 | 9 块 | 4 块 |
| B 文档最大条款组 | 第二十六条 7/51 = 14% | 第十六条 4/52 = 8% |

| A 文档页码残留 | 0 | 0 |

`inspect_chunks.py` 现在会直接报这个指标：

```
条款组：15 个    最大：第四条 -> 5 块（6%）
带条款号：41 块  |  无条款号：43 块（前言 / 附件 / 签署区）
```

**人工核对无条款号分组（这一步不能省）**：A 文档的 43 个无条款号块
正好是「错位页 + 签署区 + **附件1 到 附件15 各自成组** + 末页签署区」——
没有一个正文条款被误判。附件标题也作为组标题保留了下来。

### ⬜ 新引入的小问题：短块

附件标题独立成组时可能极短 —— A 文档实测 `附件14 养老机构规章制度` 只有 **13 字**
（下一行就是 `附件15`，所以它没有正文）。

这类块对检索是噪声。**Day 5 或 W2 可加一条最小长度阈值**（例如 < 30 字的块丢弃或合并），
但现在不加：**先看清分布再定阈值，否则会误删真实的短条款。**

### 面试价值

这一轮的价值**不在「跑通了」，而在「合成数据全绿但真实数据出问题」**：

> 「我的切分器在自建 fixture 上全部测试通过。拿真实合同 PDF 一跑，
> 发现两个 fixture 永远测不出的问题：一是 `chunk_id` 碰撞 —— 同一份文档里
> 重复出现的条款产生了相同 ID，用作文档库主键会静默覆盖；
> 二是最后一个条款吞掉了整个附件部分，42% 的块挂在『第十五条』名下。
> 前者是 ID 设计漏了位置信息，后者是条款边界只认『第X条』，
> 而附件和表格里没有条款号。」

**「合成数据全绿 ≠ 真实数据可用」** 是能讲很久的一句话。
