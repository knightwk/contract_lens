## Q1｜为什么用混合检索？RRF 解决什么问题？

**核心一句**：向量管语义、BM25 管字面，两者的漏检模式不重叠；但它们的分数量纲不可比，
所以用 RRF 按**排名**融合，而不是按分数相加。

**支撑数字**（我实测的）：

- dense `0.29 ~ 0.54`，BM25 `0.59 ~ 7.58` —— **差了近一个数量级**
- 所以直接相加 = **BM25 单方面说了算**，向量那一路基本不起作用
- RRF：`score = Σ 1/(60 + rank)`，`#1 名 ≈ 0.0164`，两路都第一 ≈ `0.0328`
  （实测 hybrid top1 正是 0.0323~0.0328）

**一个反直觉的实测发现**（这条最加分）：

- 查「第十二条」时，**BM25 反而错了** —— 它把「第十五条」排在第一位
- 原因：第十五条里**交叉引用**了第十二条，而且它更短 → **BM25 的长度归一化**让它得分更高
- 结论：**一个短条款只要"提到"某条款号，就能压过那个条款本身**
- hybrid 融合后修正了这个错误

**"怎么知道这些数字的"**：我跑了三路对比（dense / bm25 / hybrid），把分数打出来才发现的。

## Q2｜你的系统怎么保证引用可核对？

**核心一句**：材料里给每条一个**全局唯一的标识**（`chunk_id`），让模型原样引用；
事后拿回答里的标识和**本次检索到的清单**做差集，非空就是编造。

### ① 标识和定位为什么必须分开

| | 标识（`chunk_id`） | 定位（章节 · 条款 · 标题 · 页码） |
| --- | --- | --- |
| 给谁用 | 机器 / 校验器 | 人 / 模型 |
| 要求 | 全局唯一、短、**模型必须精确复现** | 可读即可，不要求抄 |

混在一个括号里会出两个问题：

1. 模型引用时得把章节、条款、标题、页码**全抄一遍** → 抄错一个字就核对不上
2. 校验器**抓不到** —— 实测第一版写成 `[来源: id 章节 条款 标题 页码]`，脚本报「标识 0 个」

**为什么用 `chunk_id` 不用 `clause_no`**：`clause_no` **会重复** ——
附件里也有「第一条」，实测那份养老合同里「第一条」出现两次。

### ② 怎么检查编造

从回答里抓出所有 `[16位十六进制标识]` → 和**本次 hits 的 chunk_id 集合**做差集 → 非空即编造。

**关键**：不是"回原文看"，而是**"这条引文是不是我这次给它的"**。
引用一条真实存在、但这次没检索到的条款，同样是无效引用。

### ③ 模型完全不引用，检查会发现吗

**原来的检查不会** —— 这是**假阳性**：

```python
cited = set(re.findall(r"第X条", answer))
unknown = cited - hit_clauses      # 空集 - 空集 = 空集
return 1 if unknown else 0          # → 返回 0，判定通过
```

**修法**：把"回答里一个标识都没有"也判为失败。

**再深一层**（跨层问题）：模型会一边说「材料中无相关内容」一边**照样填一条依据**，
因为提示词强制它永远写「依据」段。所以 `grounded` 不能由"检索有没有结果"决定，
必须由**"回答有没有真的引用"**决定。

## Q6｜LangGraph 帮你做了什么？没帮你做什么？

**核心一句**：它把 Agent 循环从「隐式状态变量 + `for` 循环」变成了「显式声明的状态 + 节点和边」——
**买到的是结构，没买到正确性。**

**我做过什么**

同一个合同审查 Agent，用手写 ReAct 和 LangGraph **各实现了一遍**，同一批问题对比。
三个问题上，两个版本的步数和预算轨迹**完全一致**，一个差 1 步。
所以我的判断是：**框架没有改变行为模式，改的是表达方式。**

### 它给了我什么

1. **状态显式化（Reducer）**
   每个字段必须声明合并策略：`messages` / `chunk_ids` 是追加，`steps` 是覆盖。
   手写版里"加"和"改"没有区别，全靠你记得别写错。

2. **思考与执行解耦**
   `agent` 和 `tools` 是两个节点，中间隔着一条边。
   手写版一整轮 `for` 里既调模型又跑工具 —— **这个解耦是结构性的，不是代码规范。**

3. **可扩展性**
   checkpoint、可视化、人工中断。手写版要加这些得自己造。

### 它没给我什么（这部分只有两个都写过才答得出）

1. **不给软着陆**
   **硬上限框架是给的** —— `config={"recursion_limit": 4}` 超出会抛
   `GraphRecursionError`（默认 25）。但它是**抛异常**，不是"告诉用户我没能完成"。
   业务层的优雅收尾（预算提示 + `budget_exhausted`）仍然得自己写。

   > 一句话：**框架给了硬刹车，不给你软着陆。**

   （补充：额度检查放哪条边也得自己想。我一开始放在 `agent → tools` 上，
   结果会 strand 住已经发出的 `tool_calls` —— 正确位置是 `tools → agent`。）

2. **不管正确性**
   A4 期间我踩了 8 个 bug：role 拼成 `assitant`、`json.load` 写成 `load`、
   工具名少个 s、`steps` 赋成了"剩余量"…… **框架一个都没挡住。**

3. **不知道你的意图**
   我把 `steps` 赋成了 `remaining`，框架只负责传值，**它不知道我想让它递增**。
   （唯一的间接帮助是：`Annotated` 强制你回答"追加还是覆盖"，让影子状态类问题更容易被发现。）

### 一个只有跑过才知道的细节

> 如果预算提示正常生效，**硬上限这条保险丝基本走不到** ——
> 模型看到"还能调用 0 次"就自己收尾了。要验证它，必须把预算提示去掉。
>
> 而且它切断时会在历史里留下「有 `tool_calls`、没有对应 `tool` 消息」的 assistant 记录 ——
> **单次运行没事，但续跑会直接 400。**

这说明：**"代码里写了"和"某条分支被验证过"是两回事。**

### 如果被追问「那你为什么还用框架」

> 因为它解决的是**结构问题**，而结构问题我靠自己改不动。
> 正确性问题我可以用测试和校验兜住；**结构问题靠自觉兜不住。**
