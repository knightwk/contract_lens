# 学习流程约定

> 制定于 Day 4。**后续每天都按这个来**，不再逐天协商。

---

## 一、为什么改流程

Day 1–3 的做法是「我给完整实现，你手敲一遍」。跑完三天下来的结论是：

**方向没错，缺的是转化环节。**

- 手敲代码的学习价值**远低于直觉** —— 学习来自「处理」，不来自「敲键」
- 真正产生学习的四个动作 —— **猜测、犯错、取舍、复述** —— 一次都没发生
- 三天里所有错误都是我发现的：fixture 长度、`chunk_id` 碰撞、GBK 编码、页序错位

**结论：问题不在于「看了范例」，而在于「范例之后什么都没有」。**

> 补充一条学习科学上的事实：对抽象推理偏弱、时间紧张的学习者，
> **范例学习（worked examples）的效率高于"自己摸索"（发现式学习）**。
> 所以拿代码是对的；错的是拿完之后停下。

---

## 二、目标重定义

**不是「能独立设计」，而是「能解释、能预测、能扩展」。**

面试实际考的是：

| 面试考的 | 需要的能力 | 在哪练 |
| --- | --- | --- |
| 讲清架构和取舍 | 能**解释** | 转化三件套的「解释」 |
| 「如果改成 X 会怎样」 | 能**预测** | 转化三件套的「破坏」 |
| 现场写一段 | 能写 | 填空 + 改写 |
| 出 bug 能查 | 能调试 | 破坏 + 验证 |

### 关于「抽象思维不强」

**设计能力主要不是智力，是模式库的规模。**

有经验的架构师"想得快"，多数时候不是推导快，而是**见过并记住了大量模式**，
直接匹配上了。这个可以积累 —— 载体就是 [`decisions.md`](decisions.md)。

**目标：W6 时那份文件有 60–80 条带取舍的模式。**
那时候你不需要临场推导，面试问什么都能接上。

## 三、代码分级

| 级别 | 内容 | 谁写 |
| --- | --- | --- |
| 🟢 **配置 / 样板** | `docker-compose.yml`、`.env`、`.gitignore`、Streamlit UI、日志配置 | **我写满** |
| 🟡 **基础设施** | `parser`、`vector_store`、`model_runtime` 的框架与注释 | **我写满**，你读 + **改写** |
| 🔴 **核心决策** | 差异化能力所在：schema 设计、切分策略、RRF 融合、Agent 编排 | **留 TODO 给你填** |

**分级不是"哪些可以不学"，是投入深度的分配。**

## 四、每日流程

### 第一段：实现

| 步 | 谁 | 做什么 | 时间 |
| --- | --- | --- | --- |
| ① | 我 | 落盘骨架：详细注释 + TODO 决策点 + 调用/流程图 + 验收清单 | — |
| ② | 你 | 读骨架与流程图，填完 TODO | 40–60 min |
| ③ | 我 | review（格式见第六节） | — |
| ④ | 你 | 按 review 修改，跑验收清单 | 20 min |

### 第二段：转化（不可省）

| 步 | 做什么 | 时间 |
| --- | --- | --- |
| ⑤ | 通读我写满的部分，**标出不懂的行**，攒着一起问 | 15 min |
| ⑥ | **改写练习**：给我写满的部分加一个小能力 | 20 min |
| ⑦ | 转化三件套：解释 / 破坏 / 记录 | 25 min |

> **①–④ 是「把东西做出来」，⑤–⑦ 是「把东西变成自己的」。**
> 只做第一段，就是 Day 1–3 的状态。

**工作日总计约 2.5–3 小时**，与既定时间预算一致。

## 五、TODO 的设计规则（对「我」的约束）

### 三条硬规则

| # | 规则 | 理由 |
| --- | --- | --- |
| **1** | **每个 TODO 必须是决策点，不是语法点** | 语法填空 = 变相抄写，成本还更高 |
| **2** | **每个 TODO 5–20 行，每天 3–6 个** | 少了就是抄，多了就变成"从零写"（慢且累） |
| **3** | **每个 TODO 必须附验收标准** | 否则你不知道自己填对没有，只能干等 review |

**规则 2 是速度与深度的平衡点。**

### 好空 vs 坏空

```python
# ❌ 坏空：答案唯一且显然，你只是在替我打字
metric_type = "___"      # 提示：IP 或 COSINE

# ✅ 好空：有多个合理选项，必须推理才能选对
# TODO(你): metric_type 用 IP 还是 COSINE？
#   提示：看 model_runtime._encode_sync 的最后几行，
#        它决定了哪个度量能省掉一次计算
```

### 骨架必须能直接跑

TODO 处 `raise NotImplementedError("...")`，保证骨架能直接 import。
这样**错误范围被隔离**，验收清单会直接指到没填的那个空。

## 六、review 输出格式（对我）

四段，缺一不可：

```markdown
### TODO-N <标题>

**你填的**：<原样引用>

**问题**：<一句话说清>

**为什么是问题**：<机制层面的解释 —— 这一段是核心，不能省>

**怎么改**：<给方向，不给答案，让你自己想>

**改完怎么验证**：<可执行命令 + 期望输出>
```

**「为什么是问题」不能省。** 没有它，你只是换了个写法，没学到东西。

**并且：填错的空要记进 [`decisions.md`](decisions.md)。** 那是模式库信噪比最高的来源。

### 文档写入分工（Day 4 起修订）

| 文档 / 内容 | 谁写 | 为什么 |
| --- | --- | --- |
| `docs/experiments.md` | **我直接写** | 实验结论都是可核查的事实，不需要"你的版本" |
| `docs/decisions.md` 的机制与 API 条目 | **我直接写** | 这类内容写错比不写更糟（Q2 的"版本号"就是写错机制的例子） |
| **`decisions.md` 的复述** | **你** | 见下 |

**修订原因**：原来写的是「条目必须你自己写」。但实测下来，
这些条目的内容多是**可验证的机制和 API 事实** —— 由我写能保证准确。

**而你真正需要练的不是"抄写机制"，是"能不能把它讲出来"。**

所以你的环节换成**复述**，而且这条不能省：

> 每积累若干条，**挑 2~3 条，合上文件，
> 用自己的话重写「反过来会怎样」那一段**，发我对照。

读一遍 ≠ 拥有它。**复述才是你的环节。**

## 七、转化三件套

### ① 解释（10 min）

合上代码，回答当天的 3 个「为什么」。

**规则：答不上来的，只回去看那一处，不要通读全篇。**
通读是低效的自我安慰；定点回看才有效。

### ② 破坏（10 min）

删掉或改掉一处，**先写下预测**，再跑验证。

| 结果 | 含义 |
| --- | --- |
| 预测错了 | **今天最大的收获**，记进 `decisions.md` |
| 预测对了 | 确认自己真的理解了 |

**必须先写预测，不能直接跑。** 直接跑就变成看热闹了。

### ③ 记录（5 min）

往 [`decisions.md`](decisions.md) 加一条。

## 八、改写练习（针对我写满的部分）

填空练的是「🔴 **该写什么**」；
**改写练的是「🟡 怎么扩展已有的东西**」。两者不能互相替代。

**做法**：给我写满的部分加一个小能力，**5–20 行**。

例：

| 改写任务 | 练什么 |
| --- | --- |
| `search_dense` 加「按 `doc_id` 过滤」 | 追踪参数一路传到 Milvus 的 `filter`，并查过滤表达式语法 |
| `chunker` 加「最小长度过滤，短于 30 字的块丢弃」 | 在流水线的哪一层加、会不会误删真实短条款 |
| `parser` 加「`.txt` 支持」 | 看 `_PARSERS` 的注册方式与 `source_type` 约束 |
| `retriever` 把 RRF 的 `k` 从 60 改成 100 | 理解 RRF 公式里 k 的作用 |

### 为什么改写优于抄写

| 方式 | 成本 | 处理深度 | 撞不撞弱项 |
| --- | --- | --- | --- |
| 抄写 | 高（200 行） | **低** | 不撞，也不学 |
| 从零重写 | 很高（200 行） | 高 | **撞**（设计是弱项） |
| **改写** | **低（5–20 行）** | **高** | **不撞** |

改写要求你：**读懂结构 → 定位改动点 → 预测后果 → 验证**。
这四步和"自己设计"的认知收益几乎一样，但只需写 5–20 行。

> 一句话：**你不是不会写代码，是没练过"判断该写什么、该改哪里"。**
> 填空练前半句，改写练后半句。

## 九、明确不做的事

| 不做 | 原因 |
| --- | --- |
| **一字不落手敲代码** | 学习来自处理，不来自敲键；而且它消耗的注意力**正是转化环节要用的** |
| 复制粘贴但**不通读** | 等于没看，还更快地骗过自己 |
| 跳过转化三件套 | **这是唯一不可省的部分** |
| 不懂的地方反复通读 | 标出来攒着问，比通读划算得多 |
| 等 W6 项目做完才开始投简历 | 见第十节 |

**唯一的硬规则：可以粘贴，但必须先通读一遍并标出不懂的地方。**

## 十、求职并行线

**W3 结束（Day 21）开始投递，不要等 W6。**

那时你已经具备：

- 本地模型 CPU 部署（**会这个的人少**）
- 条款级切分 + 混合检索 + 精排
- 领域层 + 权限 + 幂等 + 边界测试
- `conventions.md` / `experiments.md` / `decisions.md` 三份文档

**三个理由**：

1. **面试本身就是最高效的学习** —— 它直接告诉你市场在问什么，比我们猜准得多
2. **讲"进行中的项目"完全正常**，甚至更好：说明你在持续投入
3. 你现在缺的不是更多代码，是**面试反馈**。等两个月拿这个反馈，太贵

**并行两条线**：白天推进项目，同时投递、面试，把面试题带回来 ——
**面到的东西直接决定项目该补哪里。**

## 十一、一句话总结

> **代码可以拿，理解必须自己长。**
>
> 拿代码省下的时间，全部投进 **解释 / 破坏 / 改写 / 记录**。
