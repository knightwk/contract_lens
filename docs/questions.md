### 问题 1：表格乱码问题：如果 PDF 里包含复杂表格，page.get_text() 提取出来的文字行列是错乱的。你未来打算怎么处理？
- page.get_text() 默认按阅读顺序输出，表格的行列关系会丢失。如果合同涉及复杂表格，我会改用 page.get_text("dict") 或 page.get_text("blocks")，它们返回带坐标的文本块。然后根据 bbox（边界框）的 y0 坐标分组，同一行的文本拼接，从而实现表格的结构化还原。
- 如果业务需要高精度表格提取，也可以引入 pymupdf 的 page.get_table() 方法（PyMuPDF 1.23+ 开始支持）。

### 问题 2：如果 PDF 有 500 页，一次性把全文读进内存做 join，内存可能爆掉。未来打算怎么优化？
- 流式入库：解析器不返回完整 full_text，而是在遍历每一页时，直接调用后续的切片（Chunking）逻辑，把每页产生的切片存进向量库。这样内存里永远只有当前这一页 + 已生成的切片。
- 分块存储：如果必须保留全文（比如为了元数据抽取），把解析后的文本按页写入临时文件（如 parsed_pages/），只把文件路径返回给主流程。后续需要全文时再从磁盘流式读取。

面试话术：
“在我的学习版实现中，我用了全量加载便于调试。但在生产设计上，我会把解析和切片做成 Pipeline（流水线），解析一页、切一页、存一页，避免单点内存峰值。”

### 问题 3：异常是抛上去还是返回空？
决策逻辑（没有标准答案，看场景）：

方案 A（你现在的做法，抛异常）：适用于“PDF 损坏属于业务异常，需要通知用户重新上传”的场景。优点是错误不会被忽视，用户体验清晰。

方案 B（返回空字符串）：适用于“这个 PDF 只是辅助资料，缺失不影响核心功能”的场景。优点是系统健壮，不会因为一个坏文件拖垮整个服务。

面试回答套路：
“我选择抛异常，因为合同审查中，PDF 解析失败意味着后续的检索和审查完全没有依据，属于不可恢复错误，必须让用户感知到。但如果是闲聊类机器人，我可能会选择返回空，让系统继续运行。”
